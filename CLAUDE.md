# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Agnus Dei / Bede** — a self-hosted, LAN-deployed, Charlotte Mason-inspired classical homeschool AI tutor. A parent configures each student's daily plan; students connect from their own tablets. Claude (Bede persona) tutors via Socratic dialogue, agentic tools, and subject-specific personas. All student data is AES-256-GCM encrypted at rest; voice biometrics authenticate children at session start.

## Bede's Constitution

Bede's persona, ethics, and limits are governed by an immutable, tamper-evident
constitution — see **[docs/CONSTITUTION.md](docs/CONSTITUTION.md)** for the full
human-readable text (Faith/Hope/Love, the seven gifts of the Holy Spirit, the
three dimensions of human formation, the moral law — the Ten Commandments and
Christ's two great commandments, governing Bede's OWN conduct rather than
content it teaches or a basis to rule on a child's or family's beliefs; Bede
is never a spiritual advisor, that's always the parent's or the child's own
pastor/priest/deacon/minister's role — and the non-negotiable rules). The canonical,
digest-pinned source is `homeschool-api/constitution/bede.constitution.json`;
`core/constitution.py` verifies its SHA-256 digest and structure at import
time and exposes it as recursively read-only data. `main.py`'s startup
lifespan re-verifies it explicitly before database initialization — a
missing or modified constitution prevents Bede from starting at all.
`services/ai_service.py`'s `_constitution_preamble()` renders it into every
prompt that shapes Bede's behavior: the tutor persona (`_build_static_prompt`,
part of the cached static block), the parent sandbox
(`_build_sandbox_prompt`), the session summary
(`generate_session_summary`), and learner-profile synthesis
(`synthesize_learner_profile`). No parent setting, custom instruction,
retrieved content, or child prompt can override it. Changing the
foundational substance requires the change-control process in
`docs/CONSTITUTION.md`'s "Change control" section, not just an edit.

**Never measure, score, or quantify a child's spiritual engagement or
growth.** The constitution's faith dimension (`connect_to_faith`, Piety,
Fear of the Lord, the non-negotiable "never force or trivialize" and
"informs but never replaces conscience" rules) is deliberately governed
qualitatively, by rule, not tracked as a metric — unlike, say,
`LearnerBehaviorCheck`'s per-style tool-call counts. That
pattern must not be extended to faith: a child's spiritual life comes
from the child, not from a number Bede optimizes against. If a future
change proposes any kind of "faith engagement" signal, counter, or
score, that is out of scope — raise it as a question, don't build it.

**Physical safety of Bede's own suggestions.** `_physical_safety_guardrails()`
(`services/ai_service.py`, wired into the cached static prompt block via
`_build_static_prompt`) operationalizes the constitution's non-negotiable
"protect the full dignity, privacy, safety, and developmental needs of
every child" rule in a direction nothing else covered: not a child's own
reported distress or danger (that's `services/moderation.py`'s
`self_harm`/`violence` categories and `check_safeguarding`'s deterministic
patterns), but Bede's *own* free-text suggestions in ordinary hands-on
tutoring — Nature Study, Science, and Mathematics all legitimately call for
real-world physical activity in Mater Amabilis's own pedagogy. Universal
across every grade and subject (unlike grade-varying sections like
`_ai_literacy_guardrails`) — a younger child is if anything more literal
about a hands-on suggestion, never less. Tells Bede to keep any suggested
activity to safe, ordinary items already meant for a child to handle
(paper, pencils, blocks, books), never suggest heights, fire/heat, sharp or
breakable objects, throwing/forceful impact, electricity, water beyond a
sink, or ingesting anything non-food; to say so plainly when an activity
genuinely calls for a nearby adult. Two kinds of risk from the CHILD's own
proposed activity get two different responses, not one: object/environment
risk (throwing, climbing, fire) gets a warm redirect to a safe alternative
that still teaches the same idea; anything targeting the child's OWN body
— holding their breath, restricting food or water, extreme temperature
exposure, testing pain tolerance, "however it's framed" — routes instead to
the exact same stop-and-escalate as `ethical_boundaries` rule 12's
safeguarding response, never a softer swap-and-continue, with an explicit
"when in doubt, treat it as the stop" tiebreaker. That fork was added in a
follow-up design-verification pass the same day the guardrail first
shipped — the original version's hazard list only named object/environment
risk and its child-proposal handling was a single undifferentiated
"redirect," which would have under-escalated a self-harm impulse dressed
as a lesson activity. Deliberately **not** a change to
`constitution/bede.constitution.json` itself — same-status ordinary code,
changeable by normal PR review, not the constitution's own
founder-review/digest change-control process. Bede's only actual
kinesthetic tool, `invite_handwriting`, is already screen-based
(drawing/writing on the tablet canvas) and carries no physical-object risk
of its own, so this guardrail is about Bede's language, not a tool's
behavior. See `docs/SECURITY.md`'s Closed gaps for the audit that surfaced
this.

## Running the Full Stack

Full deployment instructions (Docker Compose, database choice, day-to-day
commands) live in `docs/PRODUCTION_SETUP.md` — that's the single source of
truth for `make setup`/`make update`/etc. so it doesn't drift out of sync
with a second copy here. Quick orientation: the stack is **Caddy (TLS/443)
→ nginx (UI/80) → FastAPI (API/8000)**, optionally plus a local Postgres.
`setup.sh`/`setup-gui.{bat,command,sh}` are the terminal/browser-wizard
entry points into that same deployment; `packaging/windows/` (a small Inno
Setup installer + `Setup-Bede.ps1` launcher, built by `.github/workflows/build-windows-installer.yml`)
and `packaging/unix/install.sh` (Linux — Ubuntu/Debian/Arch, x86_64/arm64
including Raspberry Pi — and macOS, Apple Silicon/Intel; unsigned, verified
instead via a checksum `.github/workflows/verify-unix-installer-checksum.yml`
keeps honest) are further, native entry points on top of the same
`setup-gui.{bat,sh}` flow, additionally offering to install Ollama and pull a
hardware-appropriate model for a family that wants Bede's AI running
entirely on that computer — both write a `local-ai.json` marker file
`scripts/setup_wizard/wizard.py` reads (and deletes once consumed) to
pre-configure that choice in the browser wizard's provider picker, invisible
on every other launch path. When that marker points at a locally-installed
Ollama, `docker-compose.yml`'s `api` service resolves it via
`host.docker.internal` — automatic under Docker Desktop (Windows/Mac), and
explicitly mapped via `extra_hosts: host-gateway` for native Linux Docker
Engine, which doesn't provide that DNS name on its own. See
`docs/WINDOWS_INSTALLER.md` and `docs/UNIX_INSTALLER.md`.

## Local Development (without Docker)

**Frontend** — Vite + React + TypeScript + Tailwind (vitest for tests):
```bash
cd homeschool-tutor
npm install
npm run dev        # http://localhost:5173 with HMR
npm run build      # tsc + vite build (type errors fail the build)
npx tsc --noEmit   # type-check without building
npm test           # vitest run
```

**Backend** — FastAPI with async SQLAlchemy:
```bash
cd homeschool-api
pip install -r requirements.txt
cp .env.example .env   # then fill in values
uvicorn main:app --reload --port 8000
# API docs at http://localhost:8000/docs  (only when DISABLE_API_DOCS=false)
```

The API requires a live PostgreSQL connection (`DATABASE_URL`) on startup — it runs `CREATE TABLE IF NOT EXISTS` and initialises AES key material from the DB. There is no in-memory fallback.

## Required Environment Variables

All from `.env` (gitignored — never commit) — see `.env.example` for the
full, current list with comments, or `docs/PRODUCTION_SETUP.md` for the
narrative version. In production mode (`PRODUCTION=true`), the API rejects
startup if any credential matches a known-weak default, if `SECRET_KEY`/
`MASTER_SECRET` is under 32 characters or `PARENT_PASSWORD` is under 8
(`reject_weak_defaults_in_production`), if `CHILD_PIN`/`DEMO_PIN`/
`SANDBOX_PIN` isn't a strong pattern (same validator — see `pin_is_strong()`
for the exact rules), if `DISABLE_API_DOCS` isn't `true` or `CORS_ORIGINS`
contains a wildcard (`reject_exposed_docs_and_wildcard_cors_in_production`
— the wildcard check runs outside production too), or if none of
`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`/`MISTRAL_API_KEY`/
`LOCAL_LLM_BASE_URL` is set (`reject_no_ai_provider_configured_in_production`
— at least one AI provider is required, but never a specific one; see
`docs/PROVIDER_ADAPTERS.md`). All four validators live in `core/config.py`.

**One credential policy, three implementations, and a test that they
agree.** `core/pin_policy.py` holds both rules: `pin_is_strong()` (shape —
6+ digits, no sequential run, repeated block, or palindrome) and
`is_published_credential()` (whether the exact value is one this repository
prints as an example, `PUBLISHED_EXAMPLE_PINS`/`WEAK_PLACEHOLDER_SECRETS`).
They are deliberately separate questions: `602656` passes every shape rule
and is still unusable, because it was the published example everywhere —
`.env.example`, `setup.sh`, the wizard's own hint and placeholder, two
docs, and `config.py`'s own error messages. When the boot-time rejection
landed in `config.py` alone, the wizard went on recommending and accepting
it, so a parent following the installer's advice got an `.env` it called
valid and a container that refused to start blaming them for "the default
dev value" — and `main` went red for five consecutive
`production-regression.yml` runs, all of them this. The policy lives in
`pin_policy.py` because it is the one module the wizard's pydantic-free
container already copies; `setup.sh` necessarily keeps a bash copy (as
`demo/src/App.tsx` does in TypeScript).
`homeschool-api/tests/test_wizard_and_api_agree_on_credentials.py` pins the
invariant in both directions — **the wizard must never accept a credential
the API will refuse to boot on** — including building the `.env` the form
produces and constructing `Settings` from it. No interface names a concrete
PIN any longer: `suggest_pin()` generates one per run in both installers,
since the only example that stays usable is one that was never committed.

**A setting in `.env` only exists if `docker-compose.yml` names it.** The
`api` service enumerates environment variables one at a time rather than
using `env_file`, deliberately — the block is a reviewable statement of what
the container receives. The obligation that follows is stated in the block's
own comment ("anything set in `.env` and NOT named here is silently
dropped"), and it had drifted badly: 22 documented settings never reached
the container, among them every `WEBAUTHN_*` value (so FIDO2 security keys
were unreachable in the packaged deployment — `mfa_service.webauthn_enabled()`
is `rp_id and origin` with no fallback), `LOCALE` (so the entire
localization feature was off, and `docs/LOCALIZATION.md`'s promise that a
family "should never discover Bede is still speaking English" could not
hold, since startup validation cannot reject a value that never arrived),
every `RATE_LIMIT_*` and `WHISPER_*` tuning knob the docs tell families to
reach for, and `RETAIN_MASTERY_PROFILES` on the same day the setup wizard
began asking a parent to choose it. The failure is silent in both
directions — pydantic falls back to the code default and the stack runs —
which in a self-hosted product is the worst shape available, since the
deployer cannot tell "I configured it wrong" from "this was never wired
up." `homeschool-api/tests/test_compose_settings_passthrough.py` now pins
three things: every setting documented in either `.env.example` is passed,
every default written in compose equals the one in `core/config.py` (two
copies of one fact, checked rather than trusted — `OPENAI_TTS_INSTRUCTIONS`
is duplicated verbatim on that basis), and every variable in the block is a
real setting (a typo there is otherwise permanent). Deliberate divergences
(`CORS_ORIGINS`, `RESEND_FROM_ADDRESS`) live in a named exemption list with
stated reasons, and a parametrized test fails if an exemption outlives the
setting it excused. Note there are **two** `.env.example` files — the root
one (Docker deployment) and `homeschool-api/`'s (local dev) — which do not
agree on which settings they document; the test treats their union as the
contract rather than requiring them to be merged. `VITE_LOCALE` is the one
setting that cannot travel this way: Vite inlines `import.meta.env.VITE_*`
at build time, so the `ui` service takes it as a **build arg** fed from the
same `LOCALE`, deciding which language the login screen paints first (both
bundles always ship; the toggle switches live).

## Architecture

### Backend (`homeschool-api/`)

```
main.py              FastAPI app + lifespan (constitution verify, DB init, encryption init, voice-model warm-up, periodic data-retention purge — see docs/DATA_RETENTION.md)
core/
  config.py          Pydantic Settings — all env vars + production validation
  constitution.py    Verifies constitution/bede.constitution.json's SHA-256 digest + structure at import time; exposes recursively read-only data (see "Bede's Constitution" above)
  database.py        Async SQLAlchemy engine, ORM models (EncryptionConfig, VoiceProfile, StudentConfig, AuditLog, LearnerProfile, LearnerBehaviorCheck, LessonBookmark, MasteryProfile, ParentSecurityKey, ParentTotpConfig, ParentCredentialOverride, ParentRecoveryCode, ParentRecoveryPin, ParentLoginLockout, and more — non-exhaustive list)
  encryption.py      AES-256-GCM; MASTER_SECRET → KEK → DATA_KEY hierarchy; all BYTEA columns encrypted
  audit.py           Encrypted audit log — every security event written independently of request transaction; log_event() also runs a sliding-window anomaly watch (repeated auth failures, JWT fingerprint mismatches, access-denied hits, a single ExfiltrationGuard block, a burst of tool invocations, one suppressed tool call, or 3 adversarial-pipeline detections — see services/ai_service.py and services/policy_engine.py below — all keyed per-IP) and, past threshold, records AuditEvent.ANOMALY_ALERT + best-effort emails PARENT_EMAIL — see docs/SECURITY.md. One rule is deliberately NOT per-IP: AI_BACKEND_FAILURE (see "AI backend failure alerting" below) is pooled across every caller, since a broken AI backend is a household-wide reliability condition, not one actor's pattern — see _GLOBAL_ANOMALY_EVENTS. log_event_nowait() fire-and-forgets the write itself (asyncio.create_task, tracked so it can't be GC'd mid-write) for hot paths like login/voice-verify, and every tool invocation during a tutoring turn, where the DB round-trip must not add to response latency
  deps.py            require_auth / require_parent / require_parent_recovery FastAPI dependencies (JWT + IP/UA fingerprint). require_auth also checks a 'cv' (credentials_version) claim on parent/parent_pending tokens against core/parent_credential.py's cached current value — a mismatch means the password changed since this token was issued, and 401s it immediately rather than letting it linger to natural expiry; see "Parent account lockout & recovery" below
  license_state.py   Effective-license resolution: DB-applied key (POST /admin/license) wins over env LICENSE_KEY; unlicensed production boots GATED instead of refusing (renewal is pasted into the parent UI, no .env edit)
  parent_credential.py  DB-backed PARENT_PASSWORD override — same "DB value wins over env, live, no restart" precedent as license_state.py, applied to the password so it's actually changeable in-app for the first time. Caches credentials_version in-process (refreshed at startup and on every change) so core/deps.py's per-request check is a sync int comparison, not a DB round trip. See "Parent account lockout & recovery" below.
  provider_state.py  DB-backed override for WHICH already-configured AI adapter (services/adapters/) serves as primary — same "DB value wins over env, live, no restart" precedent again, applied to BEDE_ADAPTER_ORDER/BEDE_FORCE_ADAPTER so a parent can move off a degraded provider (e.g. a local Ollama model) from the UI without an .env edit or restart. Caches the chosen provider name in-process (refreshed at startup, like the two modules above) since services/adapters/router.py's FailoverClient consults it on every tutoring turn. Only ever stores the NAME of an already-configured adapter, never a credential. Also holds a SECONDARY override (same DB table, key="secondary" — the primary-key column was always a string rather than a hardcoded singleton for exactly this) letting a parent pick which adapter is tried first if primary errors, meaningful once 3+ adapters are configured (e.g. openai/mistral/anthropic) since with only two the non-primary one is already the only fallback there is. See "Live AI-provider switching" below.
  parent_lockout.py  DB-backed account lockout for the parent role (10 failures/30min window → 15min lock) — the piece core/audit.py's E009 anomaly watch never provided (it alerts, never blocks). DB-backed, unlike the anomaly watch's in-memory window, so a restart can't reset an attacker's progress. See "Parent account lockout & recovery" below.
  credential_hash.py  PBKDF2-HMAC-SHA256 hash/verify for verify-only secrets (the parent password override, the recovery code) — reuses core/encryption.py's exact KDF primitive. Strictly stronger than this app's usual reversible AES-256-GCM encrypt_json for a secret that never needs to be read back in plaintext.
  middleware.py      SecurityHeaders, RateLimit (per-IP sliding window; `/voice/stream/{id}/chunk|finish|events` — the mechanics of an already-approved streaming-transcription session — get their own, more generous `voice_stream_session` bucket, separate from `voice`'s stricter new-session-start budget; see docs/VOICE_SETUP.md's rate-limit regression section for why; `/auth/recovery/*` similarly gets its own `auth_recovery` bucket, separate from plain `/auth/*` login — the burst of failed logins that trips a parent lockout must not also 429 that same parent's next call to the recovery flow that's supposed to get them back in, see docs/SECURITY.md's Closed gaps), LicenseGate (unlicensed production → only login/MFA + license endpoints answer), ExfiltrationGuard (blocks known exfiltration endpoints + scans JSON response bodies for leaked key material; SSE streams pass through untouched — see Security Constraints), InstanceIdHeaderMiddleware (diagnostic-only, not part of the security stack — see `instance_id.py` below)
  instance_id.py     `INSTANCE_ID` — resolved once at process start from `RENDER_INSTANCE_ID` (Render sets this automatically per running instance), falling back to a random `local-*` value on a self-hosted single-instance deployment. Exists to answer one question a real family's screenshot posed: `services/streaming_transcription.py`'s in-memory `_sessions` dict means a voice-stream session's `start` and the `chunk`/`finish` that follow it can land on different Render replicas under autoscaling, and the resulting 404 ("Unknown or finished streaming session") reads, from a single process's own logs, identically to a session that simply expired. `core/middleware.py`'s `InstanceIdHeaderMiddleware` stamps every `/voice/stream/*` response (success or 404 alike — it runs after the route handler either way) with `X-Bede-Instance`; `homeschool-tutor/src/hooks/diagnostics.ts` (and its demo mirror) append `instance=<id>` to the SAME debug-trace line already used to report this class of bug, so two different values on `start` vs. `chunk`/`finish` are visible directly in a screenshot — no server log access required. Deliberately scoped to `/voice/stream/*` only, not every response: `SecurityHeadersMiddleware` just above goes out of its way to STRIP server-identifying headers everywhere else, and a new one globally would cut against that on a deployment (the public demo) any visitor can reach. `main.py`'s `CORSMiddleware` call carries `expose_headers=["X-Bede-Instance"]` — without it, the demo's split-origin fetch (Cloudflare Pages frontend, Render backend) would silently drop the header before client code ever saw it, since a cross-origin `fetch()` only exposes CORS-safelisted or explicitly-exposed response headers; `tests/test_app_composition.py`'s `test_the_instance_id_header_is_actually_exposed_cross_origin` reads `main.app`'s real middleware config rather than a reconstructed replica, for the same reason that file's own `test_the_middleware_stack_is_assembled_in_the_expected_order` does (a replica test passed even after the equivalent regression was deliberately reintroduced during this work). Purely observational — no session-storage architecture changed; the actual fix (pin to one instance, or move sessions to a shared store) is still an open decision.
  security.py        JWT encode/decode; device fingerprint binding
routers/
  auth.py            POST /auth/login → JWT (embeds a `locale` claim chosen at the login screen itself — see docs/LOCALIZATION.md, and a `cv` credentials_version claim for parent/parent_pending — see core/deps.py above); GET /auth/validate; GET /auth/locales (public — which locale, if any, this deployment offers as a login-time toggle). login() also checks/records core/parent_lockout.py state and resolves the password via core/parent_credential.py (DB override wins over env) — see "Parent account lockout & recovery" below.
  mfa.py             Parent MFA enrollment/login-completion (FIDO2 security keys + TOTP, services/mfa_service.py) plus, as of "Parent account lockout & recovery" below: POST /mfa/change-password (a full parent session changing its own password — core/parent_credential.py), POST /mfa/recovery-pin/enroll + DELETE /mfa/recovery-pin and POST /mfa/recovery-code/enroll + DELETE /mfa/recovery-code (the mutually-exclusive "something you know" leg of account recovery, services/parent_recovery.py — enrolling one clears the other). GET /mfa/status now also reports recovery_secret ("pin" | "code" | null).
  recovery.py        Public (unauthenticated by necessity — a locked-out parent has no session), narrowly-scoped account-recovery flow: GET /auth/recovery/methods (which factors are enrolled — booleans only), POST /auth/recovery/webauthn/options, POST /auth/recovery/verify (requires proving >=2 of {recovery code, TOTP, WebAuthn} — never one alone; issues a short-lived "parent_recovery" token good for exactly one thing), POST /auth/recovery/reset-password (require_parent_recovery-gated, sets a new password via core/parent_credential.py). See "Parent account lockout & recovery" below.
  tutor.py           POST /tutor/chat (SSE stream) — safeguarding regex → moderation classifier → Policy Engine (services/policy_engine.py) → stream_tutor_response, see "Adversarial resilience pipeline" below; POST /tutor/summary
  pod.py             CRUD /pod/configs — parent saves, child loads by name (GET /pod/configs also rehydrates the Setup page so a returning parent edits their saved plan instead of a blank form); DELETE now cascades through services/student_deletion.py to remove ALL of that student's data (narration, learner profile, mastery, transcripts, voice, usage), not just the day's config — see docs/DATA_RETENTION.md
  voice.py           POST /voice/enroll; POST /voice/verify; POST /voice/stream/start, POST /voice/stream/{id}/chunk, POST /voice/stream/{id}/finish, GET /voice/stream/{id}/events (SSE) — server-side streaming transcription, the ONLY voice-input path for the tutor mic since browser-native SpeechRecognition was removed entirely, see services/streaming_transcription.py below and docs/VOICE_SETUP.md
  admin.py           GET /admin/status; GET /admin/audit; GET+POST /admin/license (in-app license view/renew — verified offline, stored in LicenseConfig, effective immediately); GET+POST /admin/ai-provider (in-app primary AI-provider switch) + POST /admin/ai-provider/secondary (in-app failover-provider switch, e.g. Claude vs. Mistral as backup) — see "Live AI-provider switching" below; GET /admin/agentic-loop-stats (core/api_usage.py's get_loop_stats — see "Bounded tool_result loop" below)
  narration.py       Narration assessment history + learner profile: GET/POST /narration/{student}/profile, GET /narration/{student}/assessments, GET /narration/{student}/behavior-check (parent-only processing_style-adaptation observation for TRACKABLE_STYLES — see LearnerBehaviorCheck)
  feedback.py        GET /feedback/enabled (public, gates whether the frontend shows any feedback UI at all); POST /feedback — any authenticated role (parent, child, demo visitor), routed via `services/email_service.py` to `FEEDBACK_EMAIL` over Resend, never persisted server-side beyond that one outbound email. `FeedbackRequest.category` (`models/schemas.py`) covers ordinary in-use feedback (cx/ux/content_quality/other), the demo's own "interested in plans" lead capture (`plans`) and end-of-session survey (`beta_close`), a real beta family's one-time setup-completion intake (`onboarding` — see `ParentSetup.tsx`/`BetaIntakeModal.tsx` above), and the beta period's structured survey (`beta_survey` — see "Beta surveys" below) — each gets its own email subject-line prefix (`_feedback_prefix`) so the operator's inbox stays triageable at a glance. `plans` is also the one category with its own destination: `_recipient_for` sends it to `SALES_EMAIL` when set (a real lead, not a bug report), falling back to `FEEDBACK_EMAIL` like every other category when it isn't — see `site/index.html`'s `#request-a-call` form, the marketing site's own onboarding/pricing entry point into this same pipeline.
services/
  ai_service.py      stream_tutor_response() + generate_session_summary(); _constitution_preamble() prepends the verified constitution to every persona/summary/profile-synthesis prompt. Its module-level `_client` is resolved through services/adapters/ (resolve_with_failover()), NOT hardcoded to Anthropic — see docs/PROVIDER_ADAPTERS.md
  adapters/          Provider-adapter layer decoupling the tutor from any single LLM vendor. base.py (Anthropic-shaped vocabulary + ChatAdapter Protocol), anthropic_adapter.py (returns a real anthropic.AsyncAnthropic), openai_compatible_adapter.py (ONE class translating Anthropic↔OpenAI /v1/chat/completions — covers OpenAI, a self-hosted vLLM/Qwen3-Coder server (or Ollama — anything speaking the same OpenAI-compatible endpoint), Mistral, any OpenAI-compatible endpoint), router.py (get_default_client() picks the first CONFIGURED adapter in BEDE_ADAPTER_ORDER — default "local,anthropic", never requires ANTHROPIC_API_KEY to boot; resolve_with_failover() is the Phase-6 failover client, and is what `services/ai_service.py`'s module-level `_client` actually resolves through; both honor core/provider_state.py's live DB override before falling through to the env order — see "Live AI-provider switching" below). Also exposes two small public helpers routers/admin.py's switcher uses: `configured_adapters()` (which adapters currently have credentials set) and `preference_order()` (the env BEDE_ADAPTER_ORDER/BEDE_FORCE_ADAPTER baseline). The library/self-hosted default treats a local vLLM server as primary and Anthropic as optional fallback, for the account-closure case. **The public Render demo overrides this**: `render.yaml` sets `BEDE_ADAPTER_ORDER=openai,mistral,anthropic` for the `bede-demo-api` service specifically (OpenAI primary, Mistral the default fallback, Anthropic a third, optional candidate present so it's a legitimate secondary-override choice — see below — the moment `ANTHROPIC_API_KEY` is filled in, with no redeploy). Because `_client` is a `FailoverClient`, this is LIVE failover, not just a boot-time preference: if OpenAI errors (auth/rate-limit/connection failure) on a request, that request automatically retries against whichever adapter is second in the effective order (Mistral by default, or Claude if picked as secondary) before any content streams back, with a ~60s circuit-breaker cooldown on the failed provider — see docs/PROVIDER_ADAPTERS.md (merged in PR #159; live failover wired in as a follow-up; the configurable-secondary override added 2026-08-03 alongside the fixed demo Privacy Notice, see "Public tracker & data disclosure page" above).
  moderation.py      classify_child_message() — AIUC-1 B005 automated moderation classifier (Haiku, reuses session_model/ANTHROPIC_API_KEY) run before every tutoring turn; fails open on any error, self_harm routes through the same safeguarding crisis path as check_safeguarding, prompt_injection is logged but never blocks alone — see docs/SECURITY.md. Its taxonomy also carries four adversarial-resilience categories (jailbreak_intent, policy_override_attempt, data_exfiltration_attempt, social_engineering) that `_BLOCKING_CATEGORIES`/`should_block` deliberately do NOT act on — those are read out of this same classification result by services/policy_engine.py instead, so adding them cost no second LLM call. See "Adversarial resilience pipeline" below.
  adversarial_detection.py  Tier 1 of the adversarial-resilience pipeline — free, instant, deterministic regex (`detect_tier1`) for the same four categories above, curated for near-zero false positives against ordinary K-8 Socratic dialogue; still catches the bluntest attack phrasings during a moderation-classifier outage, when Tier 2 (moderation.py, above) is unavailable. `build_signals()` merges a Tier 1 pass with the already-computed Tier 2 result into one `AdversarialSignals` for policy_engine.py — no second classifier call.
  policy_engine.py   Tier-agnostic policy stage — `decide(signals) -> PolicyDecision`. Pure function, no I/O: policy_override_attempt/data_exfiltration_attempt redirect the turn (Tier 1 hit OR Tier 2 at medium+ confidence); jailbreak_intent/social_engineering never redirect alone, mirroring moderation.py's own prompt_injection treatment — see "Adversarial resilience pipeline" below and docs/SECURITY.md.
  voice_auth.py      Resemblyzer speaker embedding + MFCC similarity scoring
  parent_recovery.py  The "something you know" leg of the >=2 factors routers/recovery.py's account-recovery flow requires — a parent picks ONE of two mutually exclusive shapes at enrollment: a recovery PIN (favored — parent-chosen, 6-12 digits, same pin_is_strong() floor as CHILD_PIN plus its own 12-digit ceiling) or a recovery code (the alternative — longer, machine-generated, higher entropy). See "Parent account lockout & recovery" below.
  transcription.py   transcribe_audio() behind TWO backends selected by settings.transcription_provider (core/config.py): "local" (faster-whisper in-process — the DEFAULT, and the only correct answer for a self-hosted family, whose whole premise is that a child's voice never leaves the LAN) or "openai" (OpenAI's transcription API). The second exists for one measured reason: ctranslate2 imports torch (~480MB RSS on import alone) whenever torch is present, putting the process at 642MB against Render's 512MB free-tier cap — bede-demo-api was OOM-killed repeatedly, and since streaming_transcription.py holds its sessions in memory in a single process, every restart destroyed every in-flight child's voice turn and reached the tablet as `startVoiceStream failed: Load failed`, i.e. the memory limit was showing up in bug reports as a voice bug. On "openai" NOTHING imports faster_whisper — the saving is the import that doesn't happen, so main.py's warm-up and preload() both check (deliberately twice, so it never depends on one call site). The demo runs on "openai" (render.yaml); it already sends the whole conversation to OpenAI and already uses OpenAI TTS, so local transcription there bought a privacy property that deployment doesn't claim. Turning it on is a DISCLOSURE change — demo/public/privacy.{html,es.html}, docs/RETENTION_POLICY.md, docs/INFORMATION_SECURITY_POLICY.md §5, docs/VENDOR_DATA_FLOW.md. A bad value, or "openai" with no OPENAI_API_KEY, fails at boot rather than at the first mic press; there is deliberately no silent fallback. `partial_passes_are_affordable()` is the one behavioral difference between the backends: streaming_transcription.py re-transcribes the WHOLE growing buffer every pass, which is free-ish CPU locally but ~5 billed requests (each re-uploading everything so far) per 20-second answer against a metered API, four of them discarded — so partials are skipped entirely on a non-local backend. The FINAL pass is never skipped on either, so what reaches Bede is identical; only the live word-by-word preview differs, and only on the demo. The local path is unchanged: used directly for voice enrollment phrases, and as the underlying per-chunk transcription call streaming_transcription.py's worker loop makes repeatedly. Serializes actual inference through an asyncio.Semaphore sized by settings.voice_transcription_max_concurrency (default 1, core/config.py) — CTranslate2's Whisper backend is itself internally multi-threaded per call, so concurrent passes from overlapping streaming_transcription.py sessions (e.g. a child pressing the mic again before the previous hold finished transcribing) don't parallelize, they thrash the same CPU cores and each pass gets progressively slower — confirmed via a live client trace where successive turns took 6.9s, then 33.3s, then never resolved. The semaphore makes overlapping callers queue instead of thrash. See docs/VOICE_SETUP.md's transcription-delay section.
```

**AI service pattern:** Two-block system prompt with prompt caching. The static block (`_build_static_prompt`) carries Bede's persona and rules and is marked `cache_control: ephemeral` — it's reused across turns. The subject block (`_build_subject_prompt`) changes per subject and is sent fresh. Tools block is also cached. The `[START]` sentinel triggers Bede's subject opener without showing a user bubble. Morning Time's subject block also layers in two verbatim-text catalogs that rotate weekly off the calendar (ISO week number, offset by `config.current_term` so families/demo visitors don't all land on the same entry the same week) rather than off any parent-set field: `services/poetry_catalog.py` (Catholic poetry/hymn-texts, grade-tagged, also shown in Living Books — English-locale sessions only) and `services/prayer_catalog.py` (traditional Catholic prayers — English or Spanish per the session's own login-time locale, Morning Time only; see docs/LOCALIZATION.md — not a global `settings.locale` read, it's threaded through as a parameter from the JWT the request authenticated with). Both give Bede a fixed, pre-reviewed text to quote VERBATIM instead of improvising from memory, since long devotional/poetic passages are exactly what a model can subtly misquote. A non-English session gets `_native_poetry_note` in poetry's place instead (same file, wired into `_build_subject_prompt` for Morning Time/Living Books whenever `locale != "en"`): Bede composes a short original reflection or verse rather than quoting a real poet's work in a language no catalog entry covers — see docs/LOCALIZATION.md's poetry co-study section for why quoting was replaced rather than translated. Sacred rule #10's own daily opening/closing prayer draws on a third, separate rotation in the same file — `services/prayer_catalog.py`'s `_DAILY_COLLECTION`/`daily_prayer_note()`, rotating by calendar DAY rather than week (this moment recurs every session day, so a weekly rotation would repeat for seven days straight) and spanning both Catholic devotional prayers and prayers in wider ecumenical Christian use (the Doxology, the Serenity Prayer, a Scripture blessing, "Now I Lay Me Down to Sleep") — never composed by Bede itself. **`moments` is tagged by each prayer's actual character, not defaulted to one slot per entry** — a prayer literally named "before study" or a bedtime rhyme stays single-moment, but a general prayer for peace or a doxology of praise honestly carries `{"opening", "closing"}` and is eligible for both. Before this distinction was drawn, the opening pool was 3 prayers deep and could repeat the identical prayer up to 4 times in a 10-school-day sprint; retagging by honest character plus two further sourced additions (St. Teresa's Bookmark; 2 Corinthians 13:14, a real closing-only benediction) bounds every prayer to at most 2 repeats across the same window — see `tests/test_prayer_catalog.py`'s own sprint-simulation test, which pins this rather than trusting it to hold as entries change. This replaced an earlier design where Bede "freshly adapted" this prayer each day; a model improvising devotional wording daily, with no human ever reviewing the actual words, is exactly the failure mode the verbatim-catalog pattern above exists to prevent, so this prayer now follows the same "select and quote VERBATIM, never invent" rule as the weekly poem/prayer instead of being an exception to it. `_session_position_note` (`services/ai_service.py`) is what actually injects the day's picked prayer text into the prompt for the first/last subject. `_guadalupe_note` (also in `services/ai_service.py`, wired into `_build_subject_prompt` for `Subject.saints`/`Subject.morning_time` only) is prose guidance, not verbatim stored text: when `locale == "es"` it gives Bede verified facts about Our Lady of Guadalupe and St. Juan Diego, since the app's single Spanish locale is deliberately framed as Mexican rather than pan-Hispanic-neutral — see docs/LOCALIZATION.md's "`es` is Mexican Spanish, not pan-Hispanic-neutral" section for the full scope rationale.

**Socratic follow-up pacing:** `_build_static_prompt`'s persona paragraph caps how many consecutive follow-up questions Bede asks on the very same idea before simplifying, offering a hint, or moving on — two rounds is the general outer limit, and when a child's answer opens several directions at once, Bede follows just one thread rather than all of them. `_STAGE_GUIDANCE[GradeStage.foundations]` (K-2) tightens this further: one simple, single-idea question at a time (never two things stacked into one question), and usually just one follow-up round before backing off — a Grammar-stage child is more easily lost by deep or compound questioning than an older one. See `docs/SOCRATIC_METHOD.md`'s pacing note, which teaches parents the same restraint for their own dinner-table questions.

**SSE streaming format:** Each chunk is `data: {"type":"text","content":"..."}`, `data: {"type":"tool","tool":"<name>","content":"..."}`, or `data: {"type":"done"}`. Tool calls are accumulated in a buffer, JSON-parsed at `ContentBlockStop`, then formatted and emitted.

**Agentic tools include:** `request_narration`, `invite_handwriting` (opens the tablet's writing/drawing canvas — the app's applied-practice step after dialogue: written narration, nature-notebook sketches, showing math work, per the child's `GradeStage`; also supports a structured, DITK-style mode via an optional `elements` list), `offer_socratic_hint`, `celebrate_discovery`, `connect_to_faith`, `show_visual_aid`, `assess_narration`, `suggest_next_subject`, `record_skill_evidence`, `record_phonics_evidence`, `record_language_evidence`. The first five render as styled cards in the UI (not chat bubbles); `assess_narration` is silent (server-side only) — besides saving the raw rubric scores to `NarrationAssessment`, `_save_assessment` also feeds them, best-effort, into `services/diagnostic/composition.py`'s composition-mastery rollup (`subject_area="composition"` in the same `MasteryProfile` table math uses — see that module's docstring for why it's a much simpler calibrated blend rather than the full CDM/IRT/KST pipeline, and `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md` §13.1); `record_skill_evidence` is stricter still — it emits nothing to the SSE stream at all, silently persisting math-skill diagnostic evidence via `_record_skill_evidence` (`services/ai_service.py`), which routes to exactly one of two backends: the real, db-backed `services/diagnostic/` (parent/child sessions) or the demo's in-memory `services/diagnostic_demo.py` (demo_code sessions only) — see `docs/diagnostic/`. `record_phonics_evidence` is the third silent tool, `subject_area="phonics"` on that same `MasteryProfile` table — but unlike the other two, it's paired with an actual pedagogical change, not just a passive rollup: `_phonics_checkin_note` (`services/ai_service.py`) nudges Bede to occasionally weave ONE quick, playful phonics/reading-foundations check into a K-2 (`GradeStage.foundations`) Language Arts session — never a drill, never announced, at most once per session (a prompt-only limit, since this tool has no visible card to scan for the way `_composition_note` scans `invite_handwriting`'s rendered title) — and `record_phonics_evidence` (via `_record_phonics_evidence`, gated a second time at the code level to that same subject/stage) is what saves the child's answer as evidence. This exists because Bede's own bundled curriculum content deliberately excludes direct phonics instruction (`data/catalog/year1.json`: "Phonemic awareness and reading practice happen alongside, not through this tutoring session") — real, calibrated phonics evidence didn't exist anywhere in the system before this. `services/diagnostic/phonics.py`'s `DOMAINS` is a fixed K-2 phonics scope-and-sequence (phonological awareness → letter sounds → CVC blending → blends/digraphs → long vowel patterns → sight words); unlike composition's independent rubric dimensions, this is a real developmental order, so its `next_steps` walks `DOMAINS` in that fixed sequence rather than sorting by probability — see `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md` §13.2. `record_language_evidence` is the fourth and newest silent tool, `subject_area="language_exposure"` on the same table — explicitly NOT a foreign-language-instruction subject (no Duolingo-style drilling, no per-word tracking); `_language_checkin_note` nudges Bede to teach ONE brief foreign word or phrase during History, Saints, or Art & Music — every `GradeStage`, unlike phonics' K-2-only gate — whenever that lesson's own content genuinely offers a natural opening (a Latin phrase for Rome, a French word for the Revolution, an Italian musical term, a saint's homeland phrase), then check back later in the same conversation whether the child remembered it. `services/diagnostic/language_exposure.py`'s `LANGUAGES` (Latin, Greek, French, Italian, German, Spanish) has no real prerequisite order the way phonics' domains do, so its `next_steps` sorts by probability (composition's approach) rather than walking a fixed sequence — see `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md` §13.3. No demo-mode backend for composition, phonics, or language exposure — real (parent/child) sessions only. `generate_session_summary` reads the math evidence back out again: `services.diagnostic.get_session_growth` computes a per-skill before/after (session-start prior vs. session-end posterior, from `DiagnosticEvidenceLog`) whenever Mathematics was covered, and a **Math Skill Growth** section is added to the parent-facing summary reporting the real movement — never a guess, and gated to the `parent` role only (never `demo_code`, whose evidence lives in `diagnostic_demo.py`'s ephemeral store instead and whose `student_name` isn't guaranteed isolated from a real family's). Requires `settings.diagnostic_evidence_log_enabled` (on by default — see `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md` §5.3).

**Tool-call defense-in-depth:** every tool call `stream_tutor_response` actually dispatches (not just attempts) is audit-logged as `AuditEvent.TOOL_INVOKED` — role, student, subject, tool name, IP/user-agent from the request — the first durable record of tool use for real (parent/child) sessions; the demo's `interaction_signals.py` structural counters are a separate, privacy-scoped, demo-only pipeline, not a substitute. `_MAX_TOOL_CALLS_PER_TURN` (6) caps how many tool calls a single turn may execute — a call past the cap is silently dropped (never executed or rendered, the child's turn is never interrupted) and logged as `AuditEvent.TOOL_CALL_SUPPRESSED`, which alerts the parent immediately (`core/audit.py`'s anomaly rules — see docs/SECURITY.md). Independent of, and a backstop under, the constitution/prompt-level guidance against misuse.

**Bounded tool_result loop:** before this, a tool call's outcome only ever reached the SSE stream/DB — Bede's own model never learned whether, say, `show_visual_aid` actually found the aid it asked for, since nothing was ever fed back as a proper `tool_result`. `stream_tutor_response` now wraps its model call in a loop, capped at `_MAX_TOOL_LOOP_ROUNDS` (3, independent of and always subordinate to `_MAX_TOOL_CALLS_PER_TURN`, which still spans every round combined rather than resetting per round). Most tool calls resolve to a fixed `_TRIVIAL_TOOL_RESULT` acknowledgment, so an ordinary turn — no tools, or only `request_narration`/`invite_handwriting`/`offer_socratic_hint`/`celebrate_discovery`/`connect_to_faith`/`suggest_next_subject` — always exits after one round, byte-for-byte the same as before this loop existed. Only two tools carry a genuinely dynamic outcome worth looping on: `show_visual_aid` (found/not-found, so a hallucinated `visual_aid_id` — previously a silent no-op — can now be recovered from in the same turn) and `assess_narration` (its already-computed rubric summary). `record_skill_evidence`/`record_phonics_evidence`/`record_language_evidence` are deliberately excluded — they keep their existing, tested, silent contract (no return value, no SSE chunk) rather than gaining a new model-visible surface. **`show_visual_aid` being reactable on a HIT as well as a miss is what made one turn able to show the same picture three times**, and the guard against it lives in that tool's own dispatch branch (`shown_aid_ids`, turn-scoped): the extra rounds a successful aid buys re-send the *cached* system block, so `_get_visual_aids_context`'s `[ALREADY SHOWN this session]` marking — computed once per turn from conversation history — still lists a picture displayed seconds ago in round 1 as un-shown. A repeat is answered `{"found": true, "already_shown": true}` plus a plain-words note rather than suppressed silently or faked as a miss, which would send the model hunting for a different id to fix a failure that never happened. Scoped to the turn and never the session, since look → put away → narrate → look again is picture study working. See `tests/test_visual_aid_not_repeated_in_one_turn.py`, the within-turn sibling of `tests/test_visual_aids_already_shown.py`'s between-turn guard. `suggest_next_subject` force-ends the loop outright (it's a terminal UI transition the frontend is already navigating away from); hitting `_MAX_TOOL_CALLS_PER_TURN` mid-round does too, since a suppressed `tool_use` block can never get a matching `tool_result` and the Anthropic API requires every `tool_use` in a turn to be answered before the next request — so the safest way to honor that contract is to never make a next request once the cap is hit. Hitting `_MAX_TOOL_LOOP_ROUNDS` while the model still wants to continue logs `AuditEvent.AGENTIC_LOOP_CAPPED` (informational — not added to `core/audit.py`'s `_ANOMALY_RULES` the way `TOOL_CALL_SUPPRESSED` is, since a legitimate turn with several reactable calls can reach it). The cached `system` block (constitution included) and `tools` block are reused verbatim on every round, so every non-negotiable rule governs round 2/3 exactly as it governs round 1 — nothing about looping changes what Bede is allowed to do, only how many round-trips one turn's response can take before the final text streams to the child. This is entirely internal plumbing: it adds no child-visible turn, no new message boundary, and has no bearing on session duration, break enforcement, or screen-time limits (`gradeTimer.ts`'s `session_cap_minutes`/hourly-break logic is wall-clock- and turn-count-based, on the frontend, untouched by how many internal model calls one turn's response takes). `tool_result` content is always fixed, server-computed structured data (a lookup hit/miss, an already-persisted rubric summary) — never raw free text, never anything sourced from outside this process — so it can never become a vector for an external instruction, from a parent-supplied field, the child's own chat text, or anywhere else, to reach the model. `_content_block_to_dict` (`services/ai_service.py`) serializes the assistant turn being replayed into the next round; it doesn't assume the real Anthropic SDK's pydantic `.model_dump()`, since `services/adapters/base.py`'s `TextBlock`/`ToolUseBlock` (the OpenAI-compatible adapter's own block shape, used for the demo's OpenAI/Mistral failover and any self-hosted local vLLM deployment) don't have one — this loop is provider-agnostic like the rest of this file. Sacred rule 14 (`_build_static_prompt`) closes a gap the loop's own design left open: a round-2/3 continuation, triggered by `show_visual_aid`/`assess_narration`'s own `tool_result` coming back, is not a new message from the child — nothing happened on their end while the model waited for it — but nothing previously told the model that, so a continuation could open as though praising a fresh answer ("Great thinking!") with no actual answer behind it. Reported as a real bug, the same failure shape as Rule 11's `[CONTINUE]`-sentinel case (a silence-timer pause on the *child's* side) applied to a second trigger (a tool-result round-trip pause of the *model's own* making) — rule 14 names that distinction explicitly rather than leaving it implicit, and cross-references rule 11 rather than duplicating its wording. `tests/test_tool_loop_round_no_affirmation.py` pins the static prompt text the same way `tests/test_continue_sentinel_no_affirmation.py` already does for rule 11 — neither test can verify live model behavior, only that the guardrail text survives.

**Agentic loop insights (analytics):** answers "is the tool_result loop above actually firing in practice, and what's it costing" — `core/api_usage.py`'s `get_loop_stats()` behind `GET /admin/agentic-loop-stats`. `ApiUsageEvent` (the existing token/cost log behind `GET /admin/status`'s usage card) is deliberately just an append-only per-call row with no turn/round id, so this can only approximate which rows belong to one turn: consecutive rows for the same student, on `settings.tutor_model`, within `_TURN_GAP_SECONDS` (5s) of each other are clustered into one "turn" — a heuristic, not an exact readback, and both the endpoint and the UI say so rather than presenting it as precise. Reports turns analyzed, how many were multi-round and their round distribution, average/max added latency for multi-round turns (`last_row.created_at - first_row.created_at` within a cluster), and `extra_round_estimated_cost_usd` — the cost of every round after a multi-round turn's first, using the exact same `estimate_cost_usd()` pricing table `GET /admin/status`'s usage card already uses, so the two numbers are consistent rather than a second, drifting estimate. `days` (default 30) is capped at 90, same size-capped convention as `GET /admin/audit`'s `limit`. `AgenticLoopInsights.tsx` (`homeschool-tutor/src/components/`, mounted from `ParentSetup.tsx` next to `AIProviderSettings.tsx`) is the parent/operator UI — a window-size control (7/30/90 days), stat tiles, and a rounds-per-turn distribution bar, with the same approximation caveat surfaced in the card's own copy. Self-contained by design: reads only from this deployment's own admin endpoint, no third-party analytics/BI tool ever sees this data.

**AI backend failure alerting:** answers "if Bede's AI backend itself is down (a crashed local model server, a revoked cloud API key, every configured provider erroring), does anyone find out" — before this, `routers/tutor.py`/`routers/sandbox.py`'s existing resilience (stall timeout + guaranteed `{"type": "done"}` on any mid-turn exception, see `test_tutor_stream_resilience.py`) meant a child just saw a friendly "try again" with nothing telling the parent/operator anything was systemically wrong. `AuditEvent.AI_BACKEND_FAILURE` is now logged (`log_event_nowait`, non-blocking) from all three streaming call sites — `routers/tutor.py`'s `/tutor/chat`, `routers/sandbox.py`'s `/sandbox/chat` and `/sandbox/demo-chat` — on both a stall (`asyncio.TimeoutError`) and any other exception, with `detail` recording the cause and, for exceptions, the Python exception type name. This feeds `core/audit.py`'s existing E009 anomaly watch, but as the one rule in `_GLOBAL_ANOMALY_EVENTS`: every other rule is keyed `(ip, event)` because it's about one actor's behavior, but a broken backend affects every device on the household's network identically — three different children on three different tablets each hitting one failure would never individually cross a per-IP threshold, so this event's occurrences are pooled across all IPs (including `ip="unknown"`, which per-IP rules skip outright) via a fixed `_GLOBAL_ANOMALY_KEY` bucket instead. 3 failures in 10 minutes (same cadence as `MODERATION_FLAGGED`/`ADVERSARIAL_DETECTED`) triggers a dedicated email — `services/email_service.py`'s `send_backend_failure_alert`/`build_backend_failure_alert_html`, deliberately a different template from `send_security_alert`'s "unusual activity"/"from address" framing (reused unchanged for every other E009 rule), since there's no single culprit address for a broken backend and calling it "unusual activity" would send a parent looking for an intruder instead of a crashed local model server. Same `PARENT_EMAIL`/Resend config, same 30-minute cooldown, same underlying `AuditEvent.ANOMALY_ALERT` durable record as every other anomaly rule — only the "which email template, and how the count is pooled" differ. Covered by `tests/test_audit_anomaly.py`, `tests/test_email_service.py`, `tests/test_tutor_stream_resilience.py`, and `tests/test_sandbox_stream_resilience.py`.

**Adversarial resilience pipeline:** `routers/tutor.py`'s `chat()` implements

```
User Input → Adversarial Detection → Policy Engine → Tutor State Machine → Action Validator → Parent/Student
```

as additive stages layered onto the pre-existing safeguarding/moderation gate, each reached only once the turn survives the one before it — no existing behavior in an earlier stage changed to build this:

- **Adversarial Detection** — two tiers, both scoped to four categories a fixed phrase list alone can't safely cover for jailbreak/policy-override/exfiltration, plus a fifth (social engineering) with no Tier 1 at all: Tier 1 is `services/adversarial_detection.py`'s `detect_tier1()`, free/instant regex; Tier 2 is `services/moderation.py`'s classifier, extended with `jailbreak_intent`/`policy_override_attempt`/`data_exfiltration_attempt`/`social_engineering` categories on the SAME single classify_child_message() call every turn already makes (no added latency or cost). Prompt injection itself is detected upstream of this pipeline and unchanged by it: `_INJECTION_PATTERN`/`_sanitize_parent_field` (`services/ai_service.py`, parent-supplied `SessionConfig` fields) plus the classifier's own `prompt_injection` category. Tool abuse detection is downstream by necessity (it needs to see actual tool calls) — that's the Action Validator stage below, not this one.
- **Policy Engine** — `services/policy_engine.py`'s `decide()`, a pure function turning `AdversarialSignals` (Tier 1 ∪ Tier 2 for this turn) into ONE `PolicyDecision`. `policy_override_attempt`/`data_exfiltration_attempt` redirect the turn (a Tier 1 hit, curated for near-zero false positives, OR a Tier 2 flag at medium+ confidence); `jailbreak_intent`/`social_engineering` never redirect alone, no matter the confidence — same reasoning `moderation.py` already documents for `prompt_injection`: ordinary K-8 roleplay/storytelling and ordinary kid impatience can resemble these categories to a classifier without being an attack, and this app's architecture has no secret for a jailbreak to actually leak. Every non-empty decision is logged as `AuditEvent.ADVERSARIAL_DETECTED` (blocking or not) — `core/audit.py`'s anomaly watch alerts a parent at 3 in 10 minutes from one IP, the same "routine boundary-testing vs. a sustained pattern" threshold `MODERATION_FLAGGED` uses.
- **Tutor State Machine** — the existing SSE dispatch loop inside `stream_tutor_response` (`services/ai_service.py`) — unchanged by this work; a turn only reaches it once Adversarial Detection/Policy Engine haven't already redirected it.
- **Action Validator** — the existing, already-shipped tool-call defense-in-depth described just above (`_MAX_TOOL_CALLS_PER_TURN`, `AuditEvent.TOOL_INVOKED`/`TOOL_CALL_SUPPRESSED`) — it validates each individual tool call the state machine actually dispatches, which is why it has to live downstream of, not inside, Adversarial Detection.
- **Parent/Student** — the SSE stream reaching `SocraticChat.tsx`, same as any other turn.

Deliberately excluded from this build: live adversarial pentesting against the running persona (humans/AI red-teamers doing that separately, outside this environment — see `scripts/adversarial_probe.py` for the existing offline probe harness). This pipeline is the deterministic/architectural defense the probing tests against, not a replacement for it.

**Parent account lockout & recovery:** answers "what actually happens if `PARENT_PASSWORD` (or the only enrolled second factor) is lost or exposed" — the gap left after the pre-production hardening pass (`docs/SECURITY.md`'s Closed gaps) made a *weak* password impossible, but said nothing about a *leaked or forgotten* one.

- **`PARENT_PASSWORD` is now changeable in-app.** It used to live only in `.env` — changing it meant a server-side file edit and a restart. `core/parent_credential.py` adds a DB-backed override that wins over the env default, live, no restart — the same precedence `core/license_state.py` already established for `LICENSE_KEY`. `POST /mfa/change-password` (`routers/mfa.py`) is a full parent session changing its own password on purpose; a deployment that never touches this sees byte-for-byte the same login behavior as before.
- **Account lockout** (`core/parent_lockout.py`) — DB-backed (survives a restart, unlike `core/audit.py`'s in-memory anomaly window), role-scoped (not per-IP — this app has exactly one parent identity, so an attacker spreading attempts across IPs should still trip it). 10 failures in a 30-minute window locks the parent role for 15 minutes; deliberately above the anomaly watch's own 5-failure email-alert threshold, so a parent who mistypes their password gets a heads-up before they'd ever actually get locked out. `routers/auth.py`'s `login()` checks/records this on every parent attempt.
- **Account recovery** (`services/parent_recovery.py`, `routers/recovery.py`) — a locked-out or password-forgetting parent's way back in without server access. Requires proving **at least 2** of three independent factors, never just one: a "something you know" secret — a recovery PIN (favored/default: parent-chosen, 6-12 digits, `pin_is_strong()`-checked like `CHILD_PIN` plus its own 12-digit ceiling) or a recovery code (the alternative: longer, machine-generated, higher entropy) — mutually exclusive, one choice at enrollment via `POST /mfa/recovery-pin/enroll` or `POST /mfa/recovery-code/enroll`, hashed like the password override, deliberately independent of both `PARENT_PASSWORD` and `CHILD_PIN` so a leak of one doesn't expose the others — plus TOTP, or WebAuthn (both reusing `services/mfa_service.py` unchanged — a recovery-flow WebAuthn ceremony is identical to a login one). `GET /auth/recovery/methods` is public and reports only which factors are enrolled (`recovery_secret: "pin" | "code" | null`, plus totp/webauthn booleans), never enough to help guess anything. Proving 2 factors issues a narrowly-scoped `parent_recovery` token (`core/deps.py`'s `require_parent_recovery`) good for exactly one call: `POST /auth/recovery/reset-password`.
- **Voice biometrics are deliberately NOT a recovery factor.** `services/voice_auth.py`'s current speaker verification has no random challenge phrase or liveness detection — a soft, parent-overridable identity signal (see its own medium-confidence "parent can override" path), not a spoof-resistant credential a security-critical recovery flow should ever accept.
- **Credentials_version — the piece that makes recovery actually end a takeover.** Every credential change (in-app or via recovery) bumps a version counter (`core/parent_credential.py`) embedded in every parent/parent_pending JWT at issuance and checked on every request (`core/deps.py`, cached in-process — not a DB round trip per request). A mismatch 401s immediately: changing the password doesn't just add a new valid session alongside whatever an attacker might be holding, it ends every other one, including that stolen token, instantly rather than at natural expiry (up to 8h). The frontend (`ParentSecuritySettings.tsx`'s change-password form) knows this and logs the parent out immediately after a successful change, rather than letting their own next click surprise-401.
- **All secrets that only ever need verifying, never redisplaying** (the password override, the recovery code) are hashed with PBKDF2-HMAC-SHA256 (`core/credential_hash.py`, reusing the exact KDF primitive `core/encryption.py`'s key derivation already depends on) rather than this app's usual reversible AES-256-GCM `encrypt_json` — a strictly stronger property for a verify-only secret.
- **Child-role lockout/recovery is deliberately out of scope.** This app's single-tenant design makes the parent the ultimate authority over the one shared `CHILD_PIN` — "recovery" for a locked-out child is simply a parent changing it, a capability that already exists, not a gap.

**Live AI-provider switching:** answers "the local model I set up is degraded/down, how do I move to a cloud provider without touching the server" — `BEDE_ADAPTER_ORDER`/`BEDE_FORCE_ADAPTER` (`core/config.py`) are plain env-loaded settings read once at process startup, so before this feature, switching primary provider meant an `.env` edit and a restart. `core/provider_state.py` adds a DB-backed override — same "DB value wins over env, live, no restart" precedent `core/license_state.py`/`core/parent_credential.py` already established — scoped to WHICH already-configured adapter serves as primary, and (see below) which one serves as the failover tried first if primary errors.

- **`GET/POST /admin/ai-provider`** (`routers/admin.py`) is the parent-facing surface: GET reports which adapters have real credentials configured (`services/adapters/router.py`'s `configured_adapters()`), which one is primary right now, and whether that's a live override or just the env order; POST switches it (`provider: "mistral"`) or clears it (`provider: null`, reverting to the env order). Picking a provider with no credentials configured is rejected (422) before it ever reaches the database — this table only ever stores the NAME of an adapter, never a credential.
- **`POST /admin/ai-provider/secondary`** answers a narrower question, added once 3+ adapters can be configured at once: with exactly two, picking primary already determines the failover (the other one is the only fallback there is), but with three or more (e.g. `openai`/`mistral`/`anthropic` all credentialed) a family might prefer Claude over Mistral as backup, or the reverse. Same live, no-restart mechanism, same `AIProviderOverride` table (`key="secondary"` — that column was always a string primary key rather than a hardcoded singleton for exactly this reason), same validation (naming an unconfigured or unknown adapter is rejected; naming the current primary is rejected too, as a no-op). `AIProviderSettings.tsx` only shows this second picker once `status.configured.length >= 3`.
- **Takes effect immediately, mid-session** — no restart. `services/adapters/router.py`'s `FailoverClient._live_order()` (what `services/ai_service.py`'s `_client` actually consults on every tutoring turn) calls `provider_state.effective_order()`, which now places the DB-overridden primary first and the DB-overridden secondary second (each only if set, configured, and distinct from the other) before circuit-breaker filtering runs. `get_default_client()` (the non-failover resolution path) honors the same overrides for consistency.
- **A `BEDE_FORCE_ADAPTER` env pin still wins.** That's a stronger, explicit operator decision — when set, `_configured_order()` only ever contains the forced adapter to begin with, so there's nothing left for either DB override to reorder.
- **A stale override degrades silently, not loudly.** If a parent's chosen provider's credentials are later removed from `.env`, `effective_order()` just falls back to the env order for that slot rather than breaking service — the override is a preference among what's configured, not itself a source of credentials.
- **`AIProviderSettings.tsx`** (`homeschool-tutor/src/components/`, mounted from `ParentSetup.tsx` next to `LicenseSettings.tsx`) is the parent UI — a one-click list of configured providers, current primary highlighted, "revert to default order" when an override is active, plus (once 3+ adapters are configured) a second list for picking the failover. Renders nothing when fewer than two providers are configured (nothing to switch between).
- Every change is audit-logged (`AuditEvent.AI_PROVIDER_CHANGED`), for both the primary and secondary endpoints.
- **The public demo uses this too, just without its own UI for it.** `render.yaml`'s `BEDE_ADAPTER_ORDER=openai,mistral,anthropic` makes Claude a legitimate secondary-override candidate for `bede-demo-api` the moment `ANTHROPIC_API_KEY` is filled in — the demo's own frontend never renders `AIProviderSettings.tsx`, but the same backend endpoints exist underneath it, so an operator with that deployment's parent credentials can call `POST /admin/ai-provider/secondary` directly to pick Claude over Mistral as its backup, live, without a redeploy. This is also why the demo's Privacy Notice (`demo/public/privacy.html`/`privacy.es.html`) and `docs/RETENTION_POLICY.md` name BOTH Mistral and Claude as possible backups rather than asserting one — see "Public tracker & data disclosure page" above.

**processing_style adaptation:** `_processing_style_note` (`services/ai_service.py`) nudges Bede's tool choice per the synthesized learner profile — kinesthetic (favor `invite_handwriting` WITH `elements`, a structured DITK task), reading_writing (favor `invite_handwriting` WITHOUT `elements`, plain written narration), visual (favor `show_visual_aid` when this subject has one available), auditory (favor oral narration/discussion/recitation — a behavioral nudge only, no tool call to count). For the three tool-backed styles, each matching call also increments `LearnerBehaviorCheck` (`_increment_behavior_check`; row lifecycle in `routers/narration.py`'s `TRACKABLE_STYLES`/`_sync_behavior_check`) — a minimal, parent-only, encrypted count of whether that profile's own nudge is actually changing Bede's behavior, surfaced on the Progress page. It is deliberately not a psychometric claim that any of these labels improves learning, and auditory is deliberately excluded from the counter — no honest tool-level signal exists for it (almost all ordinary Socratic dialogue already is auditory).

**companion_mode (setup-time preset):** `SessionConfig.companion_mode` (`models/schemas.py`) is a parent-chosen starting point at setup — `ParentSetup.tsx`'s preset picker ("Book Companion" / "A Bit More Structure" / "Full Daily Plan") — for how much of the day Bede should drive versus defer to the family's own physical books. Picking a preset pre-fills the subject list and session length below it (both remain freely editable, and the preset doesn't itself restrict which subjects can be picked). `full_plan` is the default and the only value that existed before this field — `_companion_mode_note` (`services/ai_service.py`, wired into the STATIC prompt block, `_build_static_prompt`, not the per-subject block, since it's a session-long framing) returns `""` for it, so today's prompt is byte-for-byte unchanged for every family that never touches this setting. `book_companion`/`guided` add a `<companion_mode_guidance>` block nudging Bede to anchor questions on whatever the family is already reading (via `current_unit`/`lesson_focus`) and keep a lighter tool-call footprint — meant for families new to homeschooling, or adopting AI deliberately and cautiously, per `docs/PARENT_SETUP.md`'s §5.

**Resuming an interrupted lesson ("meet me where I am"):** answers "how does a parent tell Bede exactly where an interrupted lesson stopped, instead of leaving that to Bede's own guess" — the deliberately-authored counterpart to the auto-generated bookmarks just below. `SessionConfig.lesson_resume` (`models/schemas.py`) is a list of `LessonResume` entries — the parent's own note of where a subject's last lesson actually stopped (`stopped_at`, required, plus optional `next_step`, `sticking_point`, `recorded_on`), at most one per subject. `LessonResume.subject` is a `Subject` enum member, not free text, and `SessionConfig._validate_lesson_resume` drops any entry for a subject not scheduled for that student today: a resume note can only ever point at one of the subjects Bede already teaches, so it is structurally incapable of introducing a topic outside the curriculum. `services/ai_service.py`'s `_lesson_resume_note()` renders the matching entry into that subject's prompt block (`_build_subject_prompt`, uncached) as `<lesson_resume>`: every field runs through `_sanitize_parent_field` first, and the block tells Bede to open mid-thread rather than reintroduce the subject, to never interview the child about where they got to (the whole point — it removes that seam), to be honest that the parent supplied the note rather than claim a memory of past sessions it doesn't have (non-negotiable rule 1), to keep the resumed work inside that subject, to believe the child over the note when they disagree, and to treat the note as context under `<ethical_boundaries>` 15 that never outranks the constitution or the sacred rules. A note whose required field sanitizes to nothing is dropped entirely and the subject opens fresh. **Wins over the auto-generated bookmark below:** when a subject has both a live `lesson_resume` entry and a `LessonBookmark`, `_build_subject_prompt` suppresses the bookmark note entirely rather than showing Bede two independently-worded "where we left off" accounts that could disagree — the parent's explicit note is strictly the more authoritative of the two. `_build_static_prompt`'s `[START]` opener rule (rule 9) says so explicitly: a `<lesson_resume>` block, when present, overrides rule 9's own bookmark-driven default. `ParentSetup.tsx` renders the editor as a "Pick up where we left off" panel per student, offering only that student's own selected subjects, and warns rather than silently discards when a note's subject is later deselected.

**Lesson continuity (bookmarks):** answers "how does a new day pick a lesson back up mid-thread instead of restarting cold" when the parent hasn't written a `lesson_resume` note for it — before this, continuity was entirely parent-authored (`SessionConfig.current_unit`/`lesson_focus`, both static until retyped); nothing Bede learned during a session ever fed back into the next one. `core/database.py`'s `LessonBookmark` (one encrypted row per `(student_name, subject)`, mirroring `LearnerBehaviorCheck`'s composite-key shape) holds one short, factual, Bede-authored resume-point sentence per subject — deliberately internal-only, never surfaced in the parent UI or Progress page, since (per that model's own docstring) there's no metric being computed about the child here, unlike `LearnerBehaviorCheck`'s per-style counters — so the same "no black-box signal about my kid" instinct that shaped that counter and the phonics/language check-ins argues for keeping this invisible rather than exposing it as a dashboard. **Write path:** `generate_session_summary` (`services/ai_service.py`) — already the model call that writes the parent-facing "Tomorrow's Springboard" line — is asked to also append a trailing, never-parent-shown `<<<BOOKMARKS>>>{"subject_key": "resume sentence", ...}<<<END_BOOKMARKS>>>` block, one sentence per subject actually covered that session; `_split_bookmarks_block` strips it out of the returned summary text, and `_persist_lesson_bookmarks` upserts it into `LessonBookmark` — real (`parent`) sessions only, same `db is not None` gate `generate_session_summary`'s math-growth lookup already uses, never `demo_code`. No added latency or cost: same single Haiku call as before. **Read path:** `_load_lesson_bookmark_readonly` (cached like the sibling `_load_processing_style_readonly`/`_load_mastery_vector_readonly` loaders, same `_READONLY_PROMPT_CACHE_TTL_SECONDS`) feeds `_bookmark_note`, wired into `_build_subject_prompt` for every subject (not gated to mathematics like the mastery vector) as a new note alongside `unit_note`/`lesson_note`/`resume_note` — suppressed for a subject with its own `lesson_resume` entry, see above. **Fade, never delete:** `_bookmark_note` phrases a bookmark less than 14 days old as "last time," and anything older as "a while back," rather than ever discarding it — a lapsed family should never feel like Bede silently lost their place. **The parent's own note always wins:** `_build_static_prompt`'s `[START]` opener rule (rule 9) tells Bede to reorient the child to the bookmark's resume point UNLESS `current_unit`/`lesson_focus` for today points somewhere else, since a parent retyping either field is read as a deliberate redirect, not an oversight. Cascades on student deletion via `services/student_deletion.py` like every other per-student table (see `docs/DATA_RETENTION.md`).

**The work ledger in the public demo:** the demo shows the REAL work-ledger card, and the reason it can is the same property that makes the ledger useful to a family in their first two weeks. The ledger records **events, not an estimate** — its first entry is as true as its two-hundredth, with no calibration threshold to clear — so nothing about a fifteen-minute session makes showing it dishonest. Contrast the mastery vector, which needs history the demo doesn't have and which is why `services/diagnostic_demo.py` is a single-session preview with its own `CALIBRATION_THRESHOLD`, and why phonics/literacy/language-exposure have **no** demo mastery engine at all.

- **Storage is completely separate; the computation is identical.** `core/database.py`'s `DemoCodeActivityLog` is one encrypted blob per demo code (a JSON list, read-modify-write, capped at `_MAX_DEMO_ACTIVITIES`), a standalone table for the same no-`ALTER TABLE` reason as `DemoCodeUnitNote`/`DemoCodeFaithNote`, with the identical TTL/eviction convention — swept past `_cutoff()` in `generate_code()`, deleted immediately by `end_session()`. Never `SkillActivityLog`: a demo visitor's `student_name` is whatever they typed at the code screen and is not isolated from a real family's, so sharing that table would be both a broken promise and a collision. But `services/diagnostic/activity.py`'s `summarize_records()` — extracted from `summarize()` precisely so this could happen — and `initiative_signal()` are the REAL ones, not a second implementation. A demo that shows a card the product doesn't actually produce is worse than no demo.
- **All four evidence paths feed it**, unlike the mastery engines. `_record_work_done_demo` (`services/ai_service.py`) is the demo counterpart to `_record_work_done`, and `_record_phonics_evidence`/`_record_literacy_evidence`/`_record_language_evidence` all now take `demo_code` and split: mastery only when `db is not None`, ledger either way. Otherwise a visitor who picks Living Books gets an empty card and no reason why. `_work_label()` resolves skill ids to names for both paths so they can't disagree.
- **`GET /diagnostic/demo/activity`** (`routers/diagnostic.py`) is `_require_demo_code`-only and deliberately **not** behind `_require_diagnostic_quota`, unlike `/diagnostic/summary`. That quota exists because a mastery estimate is the demo's expensive, scrapeable asset; this endpoint aggregates what the visitor themselves did minutes ago, costs nothing, and is worthless to anyone else — charging a preview use for it would be charging for the receipt.
- **`DemoWorkLedgerCard`** (`demo/src/App.tsx`, beside `ContinuingMasteryCard`) is the compact sibling of `WorkLedger.tsx` — a demo is a chat screen, not a dashboard — and follows every one of its rules: no bars, no percentages, nothing averaged, only the notable end of each scale earns a note, a note that would read zero isn't rendered, and the scored count is stated so ordinary work can't pass for work nobody watched. Refreshed by a best-effort `fetchDemoActivity` after each completed turn, since the recording tools are silent and emit no SSE chunk to react to.
- **The consent screen says so.** `consent.bullet2Ledger` sits directly under the existing "anonymized patterns — never what was said" bullet, because that is the category this belongs to: which skill was worked, how much help it took, what Bede noticed. Never the child's words. Kept for the session only, deleted on logout.

**Demo/app voice parity:** the demo's voice input is now the app's, not a lagging copy of it. It had drifted three ways at once, all of them making the demo *look worse than the product it sells* — the wrong direction for the one surface a prospective family judges Bede by. `demo/src/endpointing.ts` mirrors `homeschool-tutor/src/utils/endpointing.ts` byte for byte apart from its header, and `demo/src/endpointing.test.ts` imports **both** and asserts every constant matches, since a silence window that drifted apart would mean the demo was demonstrating something a family wouldn't get. `demo/src/useVoiceModePreference.ts` is likewise mirrored, so the demo now offers the same opt-in, off-by-default, per-device continuous "Voice on" mode, with the same two circuit breakers (`MAX_CONSECUTIVE_VOICE_FAILURES`, `MAX_CONSECUTIVE_SILENT_TURNS`) and the same `MIN_MS_BETWEEN_AUTO_STARTS` floor. The toggle reuses the app's own i18n keys (`voiceModeToggleTooltip`/`voiceModeContinuous`/`voiceModeHold`) rather than a parallel vocabulary. Two genuine bug fixes travelled with it, both previously app-only: `finishRequestedRef` (release() finished the session and the following stop() finished it *again*, a guaranteed 404 on every successful turn, filling the debug log with 404s that made a real one hard to spot) and the **stream-ended-while-still-recording teardown** — whose original trace was a *demo* trace, since it's the demo's own multi-instance session loss on Render that produces it, and without the teardown the recorder kept capturing, the mic latched on, and every subsequent press was silently refused. `bede-voice-mode` is a new `localStorage` key, so it has a row on `site/privacy/index.html` and an entry in `demo/src/privacyInventory.test.ts` — that page promises "no rounding up," which a key without a row would make publicly false.

**Continuing Mastery (demo):** the public demo's own answer to lesson continuity — deliberately a *different* mechanism from the real app's `LessonBookmark` above, not a reuse of it, because `demo_code` sessions are explicitly excluded from that table (`db=None` for the demo role — see `routers/tutor.py`'s `chat()`) and the demo's own consent screen promises "your conversation is never stored." Two independent pieces, both client-side-only within the current browser tab (`sessionStorage`/React state in `demo/src/App.tsx`, nothing new sent to or stored by the backend beyond what's below), surfaced in a "Continuing Mastery" card rendered under the subject picker in `ChatScreen`'s header (`ContinuingMasteryCard`):
- **Resuming a touched subject.** `subjectLastExchange` (React state, per-subject) is updated after every completed turn in `runStream` with that subject's REAL last exchange (Bede's actual reply text, plus the child's own message when it wasn't the silent `[START]`/`[CONTINUE]` sentinel) — never a synthesized summary, since there's no per-subject LLM bookmark call available client-side the way the real app's `LessonBookmark` write path has server-side. The card lists every subject other than the one currently open that has a recorded exchange, with a short excerpt and a "Resume →" button (`onClick={() => setSubject(s)}`). In-memory only, not persisted across a reload, mirroring the existing `openerFired` ref's own not-fully-restored posture just above it in the same file.
- **Anchoring on a lesson the family brought from outside Bede's own curriculum.** `CodeScreen` gains a third optional field (alongside name/grade) — "Continuing a lesson from home?" — a short free-text note (e.g. "reading Farmer Boy together", "our own Ancient Egypt unit"). Sent to `POST /auth/demo-code` as `current_unit` (`DemoCodeRequest.current_unit`, `models/schemas.py`), sanitized identically to `student_name` (`_sanitize_parent_field` — HTML/prompt-injection/credential stripping) since it's the second piece of free text an anonymous public visitor puts in front of the model, then stored in `core/database.py`'s `DemoCodeUnitNote` — a **new, standalone table**, not a column on `DemoCodeSession`, because this codebase's startup only ever runs `CREATE TABLE IF NOT EXISTS` (no `ALTER TABLE` migration path — see `core/database.py`'s own module docstring), so a new table is the only way to ship this to an already-running deployment without a manual schema change. Same TTL/eviction convention as `DemoCodeSession`: no expiry column, `core/demo_code_session.py`'s `_cutoff()` filters both at read time (`get_current_unit`) and in the opportunistic cleanup inside `generate_code()`; `end_session()` deletes a code's note row immediately on explicit logout, same as it does for the `DemoCodeSession` row itself. `routers/tutor.py`'s `_demo_session_config()` reads it back and sets it on `SessionConfig.current_unit` — **zero new prompt logic**: this is the exact same field a real parent's own `current_unit` already populates, so `_build_subject_prompt`'s existing `unit_note` (every subject, not just one) and the `[START]` opener rule's existing "the parent's own note always wins" precedence (`_build_static_prompt` rule 9) apply to it unchanged. The Continuing Mastery card surfaces this back to the visitor as "Following your own lesson: {note}" so they can see Bede is actually anchoring on what they typed, not just demonstrating its own bundled curriculum — this is the demo's showcase of the same `book_companion`/`current_unit` behavior `docs/PARENT_SETUP.md`'s §5 documents for real families. This one piece — a short config note, not the conversation — is the one part of Continuing Mastery that reaches the backend/database at all; it's the same category the consent screen's own "name and grade personalize this session, kept up to 6 hours" line already carves out, so that promise is unchanged, just extended to cover one more short field of the same kind.

**Two independent faith modules — Scripture & Bible Study alongside Saints & Catechism:** answers "how does Bede offer real faith-formation content to a family whose church isn't Catholic, without diluting or relabeling the existing Catholic-tradition module." Before this, `Subject.saints` ("Saints & Catechism") was the only faith-formation subject beyond Morning Time's own Bible/hymn/prayer content, and it's explicitly Catholic in scope — its `_get_catalog_context` note draws on the Ignatius Press *Faith and Life* catechism series (`data/catechism/faith_and_life.json`), covering First Confession, the Mass, and the sacraments by name. A Protestant family had no equivalent module of their own; only Morning Time's general Bible content. `Subject.scripture` ("Scripture & Bible Study," `models/schemas.py`) is a new, independent sibling subject — not a relabeling of `saints`, not a merge — so a family enables either one, both, or neither, exactly matching their own church's own categories. Its `_SUBJECT_CONTEXT` entry (`services/ai_service.py`) is deliberately denomination-neutral in Bede's own voice: Bible narrative, memory verses, and the moral law the text plainly teaches, but explicitly instructed never to assert denomination-specific doctrine (a specific catechism's structure, sacramental theology, church governance) as though every Christian tradition holds it — that stays the family's own pastor's or priest's role, per `docs/CONSTITUTION.md`'s non-negotiable rule that Bede is never a spiritual advisor. `scripture` has no catechism-style catalog of its own (`_get_catalog_context` only reaches for `get_catechism_note` on `Subject.saints`) — inventing a single "the" Protestant Bible curriculum to quote from would itself take a denominational side. What it DOES have, as of the catalog-coverage pass, is a per-year `subject_plans` entry in each `data/catalog/yearN.json` (Years 1-8): a scope of Bible narrative and themes appropriate to that year, written for this project and explicitly NOT attributed to Mater Amabilis the way `get_catalog_note`'s book listings are. Every one of those eight plans carries the same canon/translation neutrality guarantee in its own text — follow whatever Bible the family reads, never assert one tradition's canon or ordering is correct, and defer denomination-specific doctrine to the family's own pastor/priest/minister — pinned by `tests/test_catalog_coverage.py` so a future edit can't quietly drop it.

`SessionConfig.faith_tradition` (`models/schemas.py`) is a new, optional, short label for the family's own church tradition (e.g. "Baptist," "Catholic," "Non-denominational"). `_faith_tradition_note` (`services/ai_service.py`, wired into `_build_subject_prompt` for `Subject.scripture`/`Subject.saints`/`Subject.morning_time`) turns a set `faith_tradition` into framing guidance only — never denomination-specific facts the way `_guadalupe_note` supplies verified Marian-devotion history for the Spanish locale — asking Bede to avoid assuming devotional practice or doctrine outside the stated tradition and to defer denomination-specific doctrinal questions to the family's own pastor/priest. One explicit exception: `_OUTSIDE_HISTORIC_CHRISTIAN_SCOPE` is a short, documented substring list (Jehovah's Witnesses/Watchtower, Mormonism/Latter-day Saints/the Book of Mormon) for groups built on a modern individual's claimed revelation alongside or in place of the Bible. A `faith_tradition` matching it does NOT get the usual "frame content to feel at home there" accommodation — Bede keeps teaching from the historic Christian consensus `_SUBJECT_CONTEXT[Subject.scripture]` itself now defines (the faith shared across the Catholic, Orthodox, and Protestant traditions), exactly as if the field were unset, and never states this as a judgment to the child or family — it's a scope decision about what Bede itself teaches from, not an adjudication of a family's private beliefs, which stays out of scope per `docs/CONSTITUTION.md`'s "not a spiritual advisor" rule. See `tests/test_faith_tradition_note.py`.

**A third faith-adjacent module — Latin & Christian Foundations:** answers "does Bede teach Latin foundationally, in the spirit of the Christian tradition, for a family of *any* Christian tradition." Before this, Latin existed in exactly one place: `latin` as one of six languages in `services/diagnostic/language_exposure.py`, surfaced by `_language_checkin_note` as an *opportunistic* one-word-per-session moment inside History/Saints/Art & Music, whose own docstring says outright "Bede does NOT teach any language systematically." That's a readiness signal for parents, not instruction. `Subject.latin` ("Latin & Christian Foundations", `models/schemas.py`) is a real K-8 language subject, opt-in per student like every other. It sits with `scripture`, NOT with `saints`: a family holding none of the distinctively Catholic doctrines (intercession of the saints, the sacraments, transubstantiation, purgatory, the Marian dogmas) must be able to teach it start to finish and never meet them — Ave Maria, Salve Regina, the Sanctus, and the Confiteor are all deliberately absent for exactly that reason, and `tests/test_latin_catalog.py` asserts it against the rendered prompt rather than trusting the intent. `SUBJECT_DURATIONS[Subject.latin]` is 10 minutes, the shortest block in the curriculum on purpose.

`services/latin_catalog.py` is its verbatim content, following `poetry_catalog.py`/`prayer_catalog.py`'s architecture (weekly ISO-week rotation, `current_term` as per-session salt, stage-filtered entries) and their VERBATIM rule — with a stricter sourcing bar than either at authoring time: every Latin text was checked against published Vulgate editions when the file was written, while `prayer_catalog.py`'s original texts came from model knowledge because a reference site wasn't reachable during that build. (A later pass did cross-check `prayer_catalog.py` against real sources via WebSearch — see that file's own docstring — closing most of that original gap, though a direct-page WebFetch remains blocked in this sandbox the same way it was then.) The bar still matters for Latin specifically because, in an inflected language, a single wrong ending is a wrong meaning and neither child nor parent can catch it. Six foundational terms — Fides, Spes, Caritas (the constitution's own three theological virtues), Sapientia (its first gift of the Holy Spirit), Veritas, Ora et Labora — each with a verified Vulgate anchor, plus per-stage shared-Christian vocabulary. The spine is the Vulgate Great Commandment (Mt 22:37, 39), present in every stage's block. Three deliberate content decisions worth not undoing: **Sapientia cites Proverbs 9:10, not the more famous "Initium sapientiae timor Domini"** — that's Vulgate Ps 110:10 but Ps 111:10 in the Hebrew numbering most Protestant Bibles follow, so citing it would force a numbering tradition on a child in the subject's own wisdom lesson; Proverbs 9:10 carries the same reference everywhere. **`ora_et_labora` states honestly that the motto appears nowhere in St. Benedict's Rule** (it's Maurus Wolter, Beuron, 1880) and supplies `Otiositas inimica est animæ` from Rule ch. 48 to quote instead — the constitution's "never fabricate certainty" rule applied to a pleasant, universally repeated, false attribution. **Pronunciation is Ecclesiastical, stated as such**, with an explicit instruction never to correct a child taught Classical pronunciation by their own program (see `SessionConfig.curriculum_resources`).

Wiring: `_SUBJECT_CONTEXT[Subject.latin]`; `_latin_catalog_note` in `_build_subject_prompt` (gated to `Subject.latin`, locale-independent unlike `poetry_note`/`prayer_recitation_note` — the Latin text is the same text in every locale, only Bede's surrounding speech is localized); per-year `subject_plans["latin"]` in all eight `data/catalog/yearN.json` (reaching `_get_catalog_context`'s existing no-books→`get_subject_plan` fallback with no code change), each carrying the inclusivity guarantee in its own text the way `scripture`'s plans carry canon/translation neutrality. `_bible_translation_note` gains `Subject.latin` as a fourth gated subject — the Vulgate Latin is verbatim, but the English shown beside it is Douay-Rheims (the English made from that same Latin, so they line up word for word) and Bede is told to use the family's own translation's wording instead when one is set; `_faith_tradition_note` deliberately does NOT gain it, since the content needs no denominational label. `ParentSetup.tsx`'s Bible-translation gate mirrors this (Church Tradition's does not). Diagnostics reuse the existing `language_exposure` `latin` domain rather than a new `subject_area`, but `_record_language_evidence`'s gate for `Subject.latin` is *narrower* than the three opportunistic subjects', not equal: a Latin session may only record evidence for `latin` itself, and a call naming any other language there is dropped.

**A fourth faith-adjacent module — Greek & New Testament Foundations:** the companion to Latin, and answering a question Latin structurally cannot: the Vulgate is a *translation*, and Koine Greek is the language the New Testament was actually written in. For a family whose tradition emphasizes reading Scripture in its own words that is the stronger draw, and Greek is also the one classical language serving **Orthodox** families, who are served by neither `saints` (Catholic in scope) nor `latin` (the Western Church's language). `Subject.greek` ("Greek & New Testament Foundations", `models/schemas.py`), 10 minutes like `latin`. Before this, Greek existed only as one of six opportunistic languages in `services/diagnostic/language_exposure.py`, exactly as Latin did before #340.

`services/greek_catalog.py` mirrors `latin_catalog.py`'s architecture and every guarantee, and its six terms are deliberately Latin's six — πίστις/ἐλπίς/ἀγάπη/σοφία/ἀλήθεια, with **λόγος** in Ora et Labora's place (the Benedictine motto has no Greek counterpart). **Four of the six carry the SAME anchor verse as their Latin counterpart** (1 Cor 13:13, Rom 12:12, John 14:6), which is a feature, not a coincidence: a child taking both subjects meets one verse in two languages and can see `caritas` translating ἀγάπη. `GREAT_COMMANDMENT["link_to_latin"]` states that explicitly and `tests/test_greek_catalog.py` pins both the shared anchors and the link, so a future edit can't quietly decouple the two subjects.

Three things are genuinely Greek-specific, not inherited from Latin. **The manuscript question is sidestepped rather than answered:** Greek has a live, denominationally charged Textus Receptus/critical-text divide the Vulgate does not, so every anchor was chosen because both traditions read it *identically* at the quoted phrase — the same instinct as Latin's psalm-numbering decision, and the block tells Bede to take no position if a student raises it. **Transliteration and English are mandatory beside any Greek** — Latin needs no such rule, its script is already the child's own. **Pronunciation is Erasmian and labelled as a teaching convention, not a reconstruction**, with an explicit instruction never to correct a Greek-heritage or Orthodox child saying words their own parish actually uses; this matters more than Latin's Ecclesiastical/Classical note because those children exist in a way "native Latin speakers" do not. Also Greek-specific: **the alphabet IS the K-2 curriculum** (`ALPHABET`, `letters_for_week` — a couple of letters per week, not all 24 in one block, with `ALPHA_OMEGA`/Rev 22:13 as the anchor giving a five-year-old a reason to care), and **term cautions are suppressed entirely at `GradeStage.foundations`** — every caution is analytical 3+ material, and the ἀγάπη one distinguishes it from ἔρως, which must never render into a K-2 prompt just because ἀγάπη is taught at every stage. Latin needs no equivalent rule (its only K-2-reachable caution contrasts `caritas` with `amor`/`amicitia`).

**Wiring is generalized, not duplicated.** Adding Greek turned Latin's three special cases into one mapping: `_CLASSICAL_LANGUAGE_SUBJECTS` (`services/ai_service.py`) maps a `Subject` to `(catalog_note_fn, language_exposure_id)`, and all three consumers read from it — `_build_subject_prompt`'s `classical_language_note`, `_bible_translation_note`'s gate, and `_record_language_evidence`'s own-language-only gate (a Greek session may not record Latin evidence, and vice versa). A third classical language should be a row in that mapping plus a catalog module, not another branch in three functions. Per-year `subject_plans["greek"]` in all eight `data/catalog/yearN.json`, each carrying the inclusivity guarantee, the quote-never-recall rule, AND the manuscript-neutrality statement in its own text — pinned by `tests/test_catalog_coverage.py`, which now parametrizes those assertions over both classical languages.

**Logic — the trivium's second art, and the app's first stage-gated SUBJECT:** `GradeStage.core_mastery`/`independent` have always been *labelled* the Logic and Rhetoric stages (`models/schemas.py`, and `_STAGE_GUIDANCE` calls the latter "the crown of the trivium"), but nothing taught reasoning — a student got Socratic questioning without ever being told what makes an argument work. `Subject.logic` ("Logic", 15 minutes — longer than the 10-minute language blocks because one argument judged properly needs the student to reason aloud, be wrong, and be walked back through it). The label is "Logic," not "Logic & Clear Thinking": clear thinking is a real benefit the subject produces in a student who studies it well, not part of the subject's own defined name — the same distinction between a thing and its effect that keeps `<logic>` (the prompt tag in `services/logic_catalog.py`, likewise renamed from `<logic_and_clear_thinking>`) named after the subject rather than its outcome.

**Deliberately not K-2, enforced in four places rather than assumed.** Formal reasoning before the Logic stage is the premature abstraction classical education warns against. `SessionConfig._validate_logic_stage` (`models/schemas.py`) drops the subject for a foundations-stage config — "clean, never reject", the same shape `_validate_term`/`_validate_curriculum_resources` use, and ordered BEFORE `_validate_lesson_resume` on purpose so an orphaned resume note for the dropped subject is filtered in the same pass; `subjectsForStage` (`ParentSetup.tsx`) never offers the card, and feeds the minutes total too so a student moved down to K-2 stops being billed 15 minutes for a subject the backend will drop; `logic_note` returns `""` for that stage; and `data/catalog/year{1,2}.json` carry no logic plan, asserted by `tests/test_catalog_coverage.py`'s `STAGE_GATED` map. Note this is a stage-gated *subject*, unlike `_phonics_checkin_note`'s stage-gated *note* inside an ungated subject.

`services/logic_catalog.py` holds fixed, worked-out content under the same VERBATIM discipline as the language catalogs, for a sharper reason: a model asked to invent a syllogism will sometimes produce an invalid one and label it valid, and catching that is precisely what the student cannot do yet. 3-5 gets six informal `_MOVES` (oral, no technical vocabulary, no fallacy names, no syllogisms); 6-8 gets eight `_FALLACIES` and six `_SYLLOGISMS`, each with an explicit verdict — including `valid_but_false` ("All birds can fly; a penguin is a bird"), the single most important example in the subject, since a student who never meets valid-form-false-premise thinks "valid" and "true" are the same word.

**The charity guardrails are the point, not decoration.** This is the one subject where teaching the material well and forming the child well can pull against each other: a student newly able to name a fallacy has been handed a weapon, and the obvious first target is their own parents. Three guarantees travel in BOTH the prompt block and every year plan (so softening one doesn't quietly soften the feature): logic serves truth and never winning (the constitution's Love as "the final measure" governs this subject more directly than any other); Bede never coaches a child in arguing against their own parents' instructions or authority, and redirects to "state the strongest version of the other side first"; and Bede rules on no contested political, moral, or religious dispute however logically it's dressed up — teach the form with neutral examples, send the substance to the family's own pastor/priest/minister, and teach that naming a fallacy doesn't show a conclusion is false. Examples are deliberately dull (weather, animals, chores) and `tests/test_logic_catalog.py` scans every one for charged or family-shaped material.

**Wiring — two mappings, deliberately not one.** `_CATALOG_NOTE_SUBJECTS` (`services/ai_service.py`) is every subject with its own weekly stage-filtered catalog block — `latin`/`greek`/`logic` — mapped to its renderer, all sharing `(grade, stage, week_salt, today) -> str`, consumed by `_build_subject_prompt`'s `subject_catalog_note`. `_CLASSICAL_LANGUAGE_SUBJECTS` is the narrower subset that teaches a *language*, mapped to its `language_exposure` id, and is what gates `_bible_translation_note` and `_record_language_evidence`'s own-language-only check. `Subject.logic` is in the first and not the second — that split is why they're two mappings, and `tests/test_logic_catalog.py` pins it (a Logic session must not pick up a Bible-translation note).

**A defect this surfaced and closed.** `ParentSetup.tsx`'s `full_plan` preset and `blankStudent()` both computed their subject list as "every subject except `free_study`", so shipping `latin`/`greek` had silently made them defaults for every new student — 20 extra minutes and Latin in front of families who never asked, contradicting the opt-in promise those subjects are documented with. `ELECTIVE_SUBJECTS`/`DEFAULT_SUBJECTS` now name the electives explicitly (`latin`, `greek`, `logic`, `free_study`), so "Full Daily Plan" means the Mater Amabilis **core** rotation and the electives are only ever added on purpose.

**What helps this child (`learning_support`) — accommodations under stated principles, not inference:** `SessionConfig.learning_support` (`models/schemas.py`, `LEARNING_SUPPORT_SUGGESTIONS` for the quick-picks, `_validate_learning_support` for the same clean-never-reject shape `curriculum_resources` uses) is a parent-declared list of what makes a lesson go better for one particular child — more time, shorter passages, answering aloud, one step at a time. `_learning_support_note` (`services/ai_service.py`, wired into the STATIC block beside `_companion_mode_note`/`_curriculum_resources_note`, since it spans subjects) renders it as `<what_helps_this_child>`.

**Deliberately agentic-behavioural rather than algorithmic.** Bede is not running an adaptive test and is not selecting items to maximize information about a latent trait; it is a tutor told something useful about the child in front of it, acting on it with judgment inside stated bounds — the same shape as `services/policy_engine.py` (principles, not scoring) and `lesson_planner.py` (orders, never chooses). Five rules govern it and each is pinned by `tests/test_learning_support_note.py`: it changes **how** a lesson is delivered, never **what** is taught and never the standard the work is held to (*"removing an obstacle is help; removing the material is not"* — a child with more time is still judged against what the task asked, per `_WORK_SCORING_NOTE`); the child is **never told**, and never given a reason ("Let's take this one step at a time" yes, "because reading is hard for you" never); it is never a licence to praise more easily or lower a question's difficulty; Bede **never names, guesses at, or implies a diagnosis**, to the child or the parent; and where an accommodation conflicts with a lesson's form, the accommodation wins and Bede finds another route to the same end.

**Parent-declared, never inferred**, and that is the whole safety property: deciding a child needs support is a judgment about that child, reachable by a qualified evaluator or by the parent who lives with them, and Bede is neither — the constitution's own `authority_order`. `LEARNING_SUPPORT_SUGGESTIONS` is scanned by test for deficit words (`struggles`, `poor`, `unable`, `slow`…) so the list a parent reads names things to DO rather than things the child lacks; that scan is what caught "Say numbers and letters *slowly*" and got it reworded.

**Subject coverage — the schedule, never the child (`services/subject_coverage.py`, `GET /diagnostic/{student}/coverage`):** a parent could always see that History had produced nothing, and could never tell whether History was **never scheduled** (a calendar fix) or **scheduled for six weeks and opened twice** (a conversation). Opposite responses, identical-looking blank column. Both halves of the answer already existed and had never been compared: `StudentConfig` says what was scheduled, and `LessonBookmark.updated_at` says when a subject was last actually taught (written at session end for every subject genuinely covered). `STALE_AFTER_DAYS` is imported-equal to `lesson_planner`'s — one number for "long enough to notice," asserted by test rather than duplicated.

**It emits no measure of the child**, and that is enforced rather than intended: `test_it_emits_no_measure_of_the_child` scans the payload for `engagement`/`interest`/`motivation`/`effort`/`avoidance`/`score`, and `to_payload` carries the refusal in the payload itself — *"not a measure of interest, engagement, or effort… says nothing about the child"* — because a consuming model can reintroduce a judgment the data doesn't contain just by summarizing it, exactly as the pod roster becomes a ranking by summing. Same discipline as the mastery cycle's `no_evidence` (a finding about the plan) and `lesson_planner`'s reason strings. **Never-taught is its own state**, distinct from "not lately" — a subject you haven't got to is not one you are neglecting. `SubjectCoverage.tsx` (parent-only, above `WorkLedger` on Progress) also names the subjects being *kept up*, so the card isn't a list of failures a parent learns to dread opening.

**One mastery picture, not five — `MasteryOverview.tsx`:** `Progress.tsx` used to render **five separate `MasterySnapshot` cards** (mathematics, composition, phonics, language exposure, literacy), each with its own heading, evidence count, amber calibration banner and bars. They are the same component with a different `subject_area`, so a parent scrolled through five near-identical panels to assemble, in their head, the one picture the page should have shown. It also made a sentence in `docs/diagnostic/PLACEMENT_SPEC.md` impossible to write: D3's "placement results seed the normal cards" is incoherent when there is no single picture to seed — which is why the unification was recorded there as a **blocking** prerequisite (D3a) rather than a styling preference.

One card now, one row per area: each row states where that area stands in a line and opens to the detail the whole card used to be. Rows sit in a **fixed pedagogical order** (mathematics, then whichever of phonics/literacy the stage gate allows, then composition, then language exposure) — deliberately never sorted by score, since a list that reshuffles as a child improves is a ranking of their own subjects. There is **no overall score** across areas: averaging maths against language exposure would invent a quantity that does not exist and would read as a grade. An uncalibrated area still says so plainly on its row rather than showing a confident-looking bar built from four observations, and when nothing has been assessed anywhere the card points at the work ledger instead — the same advice `docs/MASTERY.md` gives a family in their first weeks. `MasteryOverview.test.tsx` pins all four.

**Work-ledger UI — `WorkLedger.tsx` and `PodWorkRoster.tsx`** (`homeschool-tutor/src/components/`, both mounted from `Progress.tsx`; the roster only when `podStudents.length > 1`). `WorkLedger` deliberately looks *unlike* the `MasterySnapshot` cards beside it: no bars, no percentages, no progress rings, because those read as "how far along is my child" (the mastery card's job) whereas this reports events. Unscored work renders as "N not scored" rather than a zero mark, so a blank stays visibly different from a low score. The initiative panel shows counts plus an explicit "not a rating of your child" caveat.

**The card never counts down, and that took two fixes the first cut missed** (found reviewing #353, fixed in the follow-up). Only the TOP of each scale earns a chip — the floors (`adequate`/`expected`/`deliberate`) are real outcomes, not deficiencies, so putting them on screen would read as marks against the work. But that created the mirror of the rule it was protecting: a skill scored honestly at every floor earned no chips, produced no "N not scored" line either, and so rendered **identically to work Bede never judged at all** — a low mark passing for a blank, the inversion of "a blank must not look like a low mark". A skill row now states its `scored` count alongside `notYetScored`, so both halves are always visible. Worse, `InitiativePanel` gated on `scored_activities === 0`, so that same student rendered `0 exemplary · 0 beyond the task · 0 brisk` under the heading **"Signs of initiative"** — three zeros under that heading is a verdict on the child, and the caveat underneath does not undo it. The panel now gates on `exemplary + beyond_the_task + brisk === 0` (which subsumes the old condition) and renders only its non-zero counts: **it reports a presence, never an absence.** `WorkLedger.test.tsx` pins both with an all-floor-scored fixture.

**Pod-roster student names travel as a repeated `students=` query parameter**, not a comma-joined value (`services/api.ts`'s `fetchPodActivity`, `routers/diagnostic.py`'s `get_pod_activity`). `student_name` is free text a parent types with no character restriction, so a name containing a comma split into two students who don't exist and the parent silently got a roster missing that child rather than an error.

**`PodWorkRoster` is the one component whose LAYOUT is a guarantee rather than a preference.** The API already refuses to emit a ranking, but a UI can reintroduce one the data doesn't contain just by choosing the wrong shape — a list of children with numbers beside them reads as a table of who is ahead regardless of what the numbers mean. So it is **grouped by skill, never by student**; students are **alphabetical within each skill** (matching the API, so the order can't shift when counts do); there is **no per-student total anywhere, not even derived client-side**; counts are rendered identically regardless of size with no emphasis on the largest; and a student who hasn't worked a skill is **absent from it**, never filled back in at zero. A skill only one student has worked is shown separately, since it has nobody to pair with. `PodWorkRoster.test.tsx` pins each of those as shape assertions rather than styling ones — including that Wren, with 19 completions to Ada's 2, still renders second.

**Scoring the work — quality, distinction, speed:** the ledger's first cut recorded only *that* a task was completed and how much help it took. That is too blunt to signify skill, so each completed activity now also carries three OPTIONAL scores, stored in the existing `detail_enc` blob (no schema change — this codebase has no `ALTER TABLE` path): **quality** (adequate/proficient/exemplary), **distinction** (expected/noteworthy/original), **speed** (deliberate/steady/brisk). Declared once as `WorkScoreFields` (`models/schemas.py`) and inherited by all four `Record*EvidenceInput` models, so a dimension is added in one place.

**The criteria are criterion-referenced and the vocabulary is a guide's, not a teacher's** — both deliberate, both load-bearing. `_WORK_SCORE_TOOL_FIELDS` (`services/ai_service.py`) declares the three fields' JSON-schema specs ONCE and splices them into all four `record_*_evidence` tools (they were duplicated four times before, which is four chances for the part most likely to be revised to drift). Each level names what the WORK looks like against **what the task asked for** — `_WORK_SCORING_NOTE` forbids comparison against another child, against what a child that age "should" do, and against how the same child did last week; the third is the subtlest because it sounds like encouragement, and it is the property that lets `pod_activity` exist at all without becoming a ranking. The note opens by telling Bede it is a **guide, not the teacher** — the parent teaches, Bede reports what it saw, and nothing recorded is "a grade, a pass, a level, or a verdict." That framing is what a model drifts away from first, since scoring vocabulary pulls toward a teacher's voice on its own, so it is asserted by test.

**`speed` means EASE, not the clock.** The wire value stays `speed` (frozen — see below), but what it records is how much the work still *costs* the child: `deliberate` = real effort and full attention, normal and good for new work; `brisk` = it barely costs them anything now. A quick answer that skipped the thinking is explicitly *not* `brisk`. Reframing it this way is what makes the dimension consistent with the standing "never hurry a child" rule instead of in tension with it, and it's the thing actually worth knowing — a skill that has stopped costing everything has freed up room for the next one.

**Enum values are frozen; criteria and labels are not.** Every level string is stored verbatim inside `SkillActivityLog.detail_enc` and there is no `ALTER TABLE` path, so renaming one would silently orphan every observation a family has accumulated (`summarize` drops values it doesn't recognize). What a level *means* and what a parent sees it *called* are both revisable without touching a stored row. Hence the split: wire `exemplary` → parent-facing "one to show", wire `noteworthy` → "went further", wire `original` → "their own idea", wire `brisk` → "came easily", and the assistance scale → "on their own" / "after a nudge" / "worked through together". `WorkLedger.tsx` carries a collapsed "what do these mean?" legend so a parent never has to leave the page for the definitions, and the card's own noun is **notes**, not scores — Bede *noticed* N, N went by *without notes*.

The governing distinction: **Bede scores the WORK PRODUCT, never the child.** "This narration was exemplary" is ordinary assessment; "this child is exemplary" is a claim this app has no standing to make, and `_WORK_SCORING_NOTE` forbids it explicitly. Three further rules in that note matter as much as the scales: **omit any dimension not genuinely observed** (a missing score is honest and must stay distinguishable from a low one — `test_scores_are_optional_and_absence_is_distinguishable`); **never hurry, time, or mention pace to a child** (a child who feels raced produces worse work, and `deliberate` is a description rather than a deficiency — every scale's floor is a real outcome, with no "poor" and no "slow"); and **`original` stays rare**, reserved for a genuine idea or method of the child's own, or the signal stops meaning anything.

`distinction` is the load-bearing dimension and the reason it isn't folded into quality: correctness cannot distinguish a student who answered the question from one who answered it and then asked a better one, and it is the second that shows initiative. `activity.initiative_signal()` is the learning-entrepreneur read built on it — counts of work done exemplarily, taken beyond the task, and done briskly, plus the skills where that happened. Deliberately **no threshold, badge, type, or verdict**: a learning entrepreneur is not a category Bede is competent to place a child in, so it reports counts and the parent draws the conclusion. `summarize()` still emits **distributions, never averages** — a mean over an ordinal scale would invent precision the scale doesn't carry and read as a grade for the child.

**The work ledger — measuring by evidence of activity, not by inferred trait:** `core/database.py`'s `SkillActivityLog` + `services/diagnostic/activity.py` record what a student has actually DONE, alongside (never instead of) the mastery engine. The two answer different questions and both are wanted: `MasteryProfile`/`DiagnosticEvidenceLog` hold a psychometric claim ABOUT THE CHILD ("0.47 probability of having mastered multi-digit multiplication"); the ledger holds an event ("on this date, a multi-digit multiplication task was completed unaided"). One row per completed activity, `detail_enc` = `encrypt_json({skill_id, label, assistance, subject_area})` — same derived-not-raw privacy class as `NarrationAssessment`. Written from all four evidence paths via `_record_work_done` (`services/ai_service.py`), best-effort so a ledger failure never blocks the mastery write that already succeeded or reaches the child's turn. Cascades on student deletion.

Three deliberate refusals, each pinned by `tests/diagnostic/test_activity_ledger.py`: **`incorrect` writes no row** (a missed attempt isn't completed work, and logging it would make this a record of failures — the mastery engine already captures struggle); **`summarize()` emits no average, level, percentage, or score**, only counts and dates, because each of those collapses a work record back into a judgment of the person; and **`pod_activity()` emits no ranking** — no per-student total, no ordering by any measure (students sort by NAME so the order can't shift when the amounts do), and a student with no work in a skill is simply absent from its roster rather than listed at zero beside a sibling's count. `assistance` (unaided/with_a_hint/with_help) is factual, describing how the work went rather than how able the child is.

This is what makes a pod workable as a self-managed team without ranking children: "who has done this work" is ordinary for a team to know and is how one member comes to help another; "who is better at this" is not built. `GET /diagnostic/{student}/activity` and `GET /diagnostic/pod/activity` are both `require_parent` and never surfaced to a child — a child who can see they are behind a sibling has been ranked whatever the UI calls it. Note `/diagnostic/pod/activity` is declared BEFORE `/diagnostic/{student_name}/activity` because FastAPI matches in declaration order and the parameterized path would otherwise swallow it as `student_name="pod"`.

**Reading & spelling for grades 3-8 — `services/diagnostic/literacy.py`:** literacy measurement previously stopped at the end of 2nd grade. `phonics.py` covers K-2 decoding (gated to `GradeStage.foundations`), `composition.py` measures writing from narration rubrics, and between them there was **nothing for reading in grades 3-8 and no spelling anywhere in the codebase at any grade** — a 5th grader could work with Bede for a year and produce zero evidence about how they read. New `subject_area="literacy"` on the same `MasteryProfile` table, following `phonics.py`'s architecture (self-contained module, simple calibrated blend, not the full CDM/IRT/KST pipeline) rather than the math engine. Ten `DOMAINS` structured on the Simple View of Reading / Scarborough's Reading Rope — word recognition (`decoding_multisyllable`, `spelling_patterns`, `morphology`, `spelling_homophones`, `fluency`) then language comprehension (`vocabulary`, `literal_comprehension`, `inference`, `text_structure`, `author_craft`) — and, like phonics, **`next_steps` walks `DOMAINS` in developmental order rather than sorting by probability**, because a child still decoding is not helped by being pointed at author's craft however low that number is. Wiring: `record_literacy_evidence` (a fourth silent tool), `_record_literacy_evidence` and `_literacy_checkin_note` both gated to `language_arts`/`living_books` × `core_mastery`/`independent` — the stage gate matters because a K-2 session must fall through to `phonics.py`, never to this engine, and `tests/diagnostic/test_literacy.py` asserts the two domain sets don't overlap. Registered in `routers/diagnostic.py`'s `_SUMMARY_BUILDERS`. The check-in is deliberately **observational, not probing**: reading evidence is already lying around in an ordinary lesson, and the prompt forbids inventing an exercise to generate it. Spelling gets three of ten domains on purpose — English is opaque (`sign` → `signature`) in a way a transparent orthography like Finnish is not, so an English curriculum needs *more* explicit word study, not less.

**Classical-language companion mode** — `_classical_language_companion_note` (`services/ai_service.py`, gated to `_CLASSICAL_LANGUAGE_SUBJECTS` and to `curriculum_resources` being non-empty) tells Bede that when a family runs their own Latin or Greek course, THEY own the sequence: the child's own lesson material outranks the weekly catalog term, their course's terminology wins over Bede's, Bede never presents its term as "the lesson", and it defers rather than pre-empting what their course will cover later. `_curriculum_resources_note` already asked Bede to align terminology, but it lives in the STATIC block and is deliberately generic across math/writing/phonics publishers — it says nothing about who owns a *sequence*, which is the thing that actually competes with a real syllabus. Keyed off `curriculum_resources` being set at all rather than pattern-matching publisher names, since a name list would be wrong the moment a family typed something unexpected and the guidance is safe either way. Parent fields are `_sanitize_parent_field`'d, asserted by test.

**Year plans teach what the skill map measures** — raising the map (above) without raising `data/catalog/yearN.json`'s `mathematics` plan would have produced a diagnostic probing for material the prompt never introduces, which reads to a parent as their child failing at things Bede never taught. All eight plans now match the expanded scope, with grade 7 stated as "pre-algebra completed, Algebra I begun", grade 8 as a full Algebra I year explicitly framed against prep-school rather than conventional expectations, and grade 5 named as the last year of pure arithmetic. `tests/diagnostic/test_prep_school_scope.py` pins ~27 (year, competency) pairs so the two can't drift apart again.

**Progress page shows Reading & Spelling for grades 3-8** — `Progress.tsx` gains a `literacySummary` card gated on `activeStudentIsBeyondFoundations`, the exact complement of the existing `activeStudentIsFoundations` gate that shows phonics only to K-2. The two never both render, mirroring the backend handoff (phonics owns K-2 decoding, `services/diagnostic/literacy.py` owns 3-8), so no student ever sees two competing reading pictures and neither card is shown where it could never have data.

**Math skill map targets preparatory-school scope (42 → 95 skills):** `services/diagnostic/skill_map.py` originally tracked a conventional public-school K-8 scope, topping out at two-step equations and a first look at linear functions — but a prep-school 8th grader normally *finishes Algebra I*. The top band now carries multi-step/literal/both-sides equations, inequalities, systems, exponent laws, radicals, scientific notation, irrationals, polynomial arithmetic, factoring, quadratics by factoring, slope and slope-intercept form, the Pythagorean theorem, transformations/similarity/surface area, and scatter plots with a line of best fit; 3-5 gains the arithmetic pre-algebra assumes is finished (order of operations, factors/primes, all four decimal operations, dividing fractions); K-2 gains Singapore-style number sense (number bonds, skip counting, equal groups). **Strictly additive** — no existing id, label, band, or prerequisite changed, because `MasteryProfile` stores `encrypt_json({skill_id: probability})` and those ids are the only link to a family's history, with no migration path for an encrypted blob. `tests/diagnostic/test_prep_school_scope.py` pins all 42 original ids plus the structural invariants (no cycles, no dangling prerequisites, no prerequisite in a higher band than its dependent, a probe for every skill). `mastery.ensure_complete()` is what makes growing the map safe at all: every consumer iterates the VECTOR rather than the map, so a vector stored before the extension wouldn't crash — the new skills would just be permanently invisible for the longest-standing families. Both load paths in `services/diagnostic/__init__.py` now backfill against the current map (band-aware on the write path; neutral 0.5 on the render path, which has no grade available since `MasteryProfile` stores no band and there's no `ALTER TABLE` path). See `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md`.

**Phase 5 tuning — the engine measured against ground truth:** `services/diagnostic/mastery.py`'s `TUNED_PARAMS` and `tests/diagnostic/test_convergence.py`. Phase 1's acceptance test feeds all-correct evidence up a prerequisite chain, which proves the vector moves in the right DIRECTION but structurally cannot catch a wrong verdict — every answer in it is correct. `test_convergence.py` generates students with a known, prerequisite-closed knowledge state, samples answers from the DINA response model, and scores the engine's own verdicts against the truth it started from. Two things came out of it. **First, a defect that blocked the tuning itself:** `bayesian_update` never passed `params` to `cdm.update_attribute_posteriors`, so the slip/guess values Phase 5 exists to tune were unreachable from the path that used them. **Second, the finding:** accuracy was not uniform across children and the bias ran backwards — a student who truly knew 15% of the map drew a false-secure verdict (told "secure" on a skill they don't have — the error that sends a family PAST a gap) on 9.3% of skills, versus 0.8% for a student who knew 85%. Structural, not a bug: `guess` is P(correct | not mastered), so understating it mis-credits lucky answers, and a struggling child produces far more not-mastered attempts to mis-credit. `guess` 0.20 → **0.25** roughly halves it at every level (9.3%→4.9%, 3.0%→1.7%, 0.8%→0.5%) for ~10 points of coverage; 0.25 is the knee, and raising the "secure" cutoff instead was measured and rejected (twice the coverage cost, and WORSE overall accuracy under a messy world). `CALIBRATION_THRESHOLD` was swept 1→20, moved accuracy 0.3pp, and was left at 5 — the `[to verify final N]` flag is now a measured decision rather than an open question. The test file states its own limits plainly: it simulates from the same model the engine assumes (one case deliberately breaks that), and it measures the ESTIMATOR, not whether real tutoring actually produces the evidence volumes assumed — that is unit 5.1, which needs a live stack and is recorded as blocked in `docs/diagnostic/DIAGNOSTIC_BUILD_PROGRESS.md` rather than quietly skipped.

**Mastery estimates that don't outlive the session (`RETAIN_MASTERY_PROFILES`):** answers "can Bede assess rigorously without keeping a psychometric claim about a child on disk". `core/config.py`'s `retain_mastery_profiles` defaults to `True`, which is today's behaviour byte for byte; setting it `False` runs the identical diagnostic but holds the estimate in `services/diagnostic_session.py` (in-memory, keyed by session, 6h TTL, bounded) instead of `MasteryProfile`, and writes nothing describing the child. **Deployment-wide, not per-child** — a privacy posture should be a property of the installed software rather than a checkbox to remember per student, and one sibling carrying a retained profile while another doesn't is hard to explain and easy to get wrong (D1 in the spec). The position is one this codebase already drew: `MasteryProfile`/`DiagnosticEvidenceLog` hold a *claim about the child*, `SkillActivityLog` holds an *event* — so the work ledger is deliberately **unaffected** by this setting and keeps recording what was actually completed. `_record_skill_evidence` gains a third branch, checked BEFORE the `db` branch so a configured database can never become a silent fallback. The key is the session (`TutorRequest.session_id`, minted in `sessionStore.ts`'s `startSession()`, deliberately not persisted — a reload starts a fresh estimate rather than resurrecting the old one); keying by `student_name` would have quietly recreated the accumulating profile being removed. **The cost is real and stated rather than hidden:** `CALIBRATION_THRESHOLD` is 5 and flagged in-code as untuned, mathematics is a 20-minute block, and evidence is opportunistic — so one sitting lands near the calibration floor and these families see "still getting to know your learner" more often. Same single-process in-memory limitation as `services/streaming_transcription.py`. Reads are wired too, and were the loose end the first cut left: `live_vector()` feeds the session estimate into `_diagnostic_context` so Bede's questioning adapts *within* the sitting (without it, evidence accumulated in memory and nothing ever read it back, defeating the whole reason for accumulating across a session), and `generate_session_summary` reports a **Math Skills Today** section from the session snapshot before calling `discard()` — the summary is the one moment the estimate is delivered, and the last moment it's needed. The Progress page's mastery cards are deliberately empty on this setting: a parent opening Progress later isn't in the child's session and has no way to reach an in-memory estimate, which the spec now states rather than implying. **Reachable from the installer, not only from `.env`:** `scripts/setup_wizard/wizard.py` asks the question directly ("Should Bede remember what your child has mastered between sessions?", default yes) and writes `RETAIN_MASTERY_PROFILES=false` ONLY when a parent actively picks no — so silence, a "yes", and the code default all agree, and an ordinary install's `.env` never restates a default back at itself. A privacy posture reachable only by hand-editing a file is not actually offered to the families this wizard exists for. `tests/diagnostic/test_ephemeral_diagnostic.py`'s first 11 cases all assert **refusals** (empty tables against a real DB), since the failure mode is silent persistence rather than a visible error; verified to fail 8 of those 11 when the branch is bypassed. Four further cases cover the read paths, including that reading the live estimate does not consume it. Still open: D3, whether an estimate deserves its own key scope separate from `StudentKey` so it can be crypto-shredded without taking the family's whole record with it. See `docs/diagnostic/EPHEMERAL_DIAGNOSTIC_SPEC.md`.

**Mastery cycle — a cadence between the session summary and the term:** `term_mastery_topics` is scored across a whole term (9-12 weeks), and `Progress.tsx`'s `statusFor` took the best level EVER recorded for a topic with no time window at all — an assessment from ten weeks ago counted exactly as much as one from yesterday. That read structurally cannot answer "did this move lately", which is the question a parent has between term reports, and which the learner's guarantee (written in 30 days) actually depends on. `SessionConfig.travel_mode` / `mastery_cycle_days` (`models/schemas.py`, mirrored in `types/index.ts`; no migration needed — `StudentConfig.config_enc` is an encrypted JSON blob) plus `utils/masteryCycle.ts`'s `readCycle()` add that window. **It bounds the LOOKING, never the child's work** — a sprint commits that scope is finished by a date, which pointed at a child is a deadline on a person and contradicts `_WORK_SCORING_NOTE`'s standing rule never to hurry, time, or mention pace to a child. Deliberately a **rolling** window rather than a numbered cycle with a start date: no boundary to hit, nothing resets, nothing rolls over, and no velocity can be computed across cycles (the same refusal `summarize()` already makes about averaging an ordinal scale). Three outcomes, and the third is load-bearing: `moved` (real evidence of advance), `held` (worked, no visible movement — normal, and deliberately earns no chip, since marking it would read as a flag), and `no_evidence` — **a finding about the PLAN, not the child**, surfaced at the core-area level as "check it is scheduled often enough" rather than beside the child's topic like a score. Same discipline as `WorkLedger`'s "a blank must not look like a low mark". `now` stays an all-time high-water mark that the window can never lower — a child who demonstrated mastery in week two has demonstrated it. Default 28 **actual** (calendar) days; `travel_mode` is the only control, and is what *unlocks* widening to 3-6 weeks for a family whose weeks away don't fit the usual evidence into 28 days — with it off there is one honest window, so `_validate_term` forces the default back (the same "clean, never reject" shape it already applies to `term_mastery_topics`) and the parent is never asked to pick a number. Parent-only; a child never sees a cycle. See `tests/test_mastery_cycle.py` and `utils/masteryCycle.test.ts`.

**Stated intent vs. capacity (mastery-based outcomes):** `session_cap_minutes` is WALL-CLOCK time and includes `gradeTimer.ts`'s mandatory 10-minute break each hour; a subject list is INSTRUCTION time. Nothing reconciled the two, and they had silently diverged — `COMPANION_MODES`' `full_plan` preset scheduled `DEFAULT_SUBJECTS`' **185 minutes** of subjects into a hardcoded **120-minute** cap, which holds only 110, so ~75 minutes of every default day were structurally unreachable and the only symptom was the timer hard-stopping mid-subject. `studyMinutesWithinCap()`/`capForStudyMinutes()` (`utils/gradeTimer.ts`, exact inverses of each other) make the arithmetic explicit, and **every preset's `sessionCapMinutes` is now derived from its own subject list** rather than typed in, so the two can't drift again: book_companion 65→75, guided 100→110, full_plan **185→215**. `blankStudent()`'s cap is derived the same way; `formFromConfig`'s `?? 120` fallback and `models/schemas.py`'s `session_cap_minutes` default are deliberately left alone so an existing saved config keeps whatever the parent chose. `ParentSetup.tsx` renders `totalMin / availableStudyMin` together and warns (with the exact cap needed) when subjects exceed capacity — the mismatch used to be invisible. `src/utils/sessionCapacity.test.ts` pins the inverse relationship, the 185/215 figures, and that every preset fits its derived cap. Note the 4-hour structural ceiling (`MAX_SESSION_CAP_MINUTES`) means the full plan PLUS all three electives (220 min) genuinely cannot fit one sitting — asserted as a known fact rather than left to surprise a family.

**Suggested (not mandatory) 20-minute breaks for K-3:** `getSuggestedBreak(phase, isYounger)` (`utils/gradeTimer.ts`) — a younger child's attention is shorter but not uniformly so, and stopping a settled six-year-old dead at 20 minutes wastes the best stretch of their morning, so the 20-minute rhythm is OFFERED rather than imposed. Returns `{mark, key}` at the 20- and 40-minute marks **of each 60-minute study block**, `null` otherwise. Derived from the session's own `PhaseInfo`, so it can never disagree with the mandatory rhythm it sits inside: null during any mandatory break, null once concluded, null for grades 4-8 (the 60/10 cycle already IS their pacing), and structurally incapable of a third mark (`floor(3599/1200) = 2`). **Nothing here can shorten, skip, delay, or extend past the mandatory hourly break** — `tests/…/sessionCapacity.test.ts` asserts each of those. `TutorSession.tsx` renders it as a dismissible *banner* (not the full-screen overlay a mandatory break gets, which still has no dismiss button): "Yes, let's pause" → a voluntary full-screen break the child ends themselves, no countdown; "No thanks, keep going" → dismissed until the next mark. Both `dismissedBreakKey`/`acceptedBreakKey` store the suggestion's own **key** rather than a bare boolean, which makes them self-clearing — a voluntary break cannot outlive its mark, survive a mandatory break, or leak into the next hour, and so needs no cleanup effect (which matters because every hook in that component must be declared before the `sessionConfig` guard). `isPaused = isOnBreak || voluntaryBreakActive` is what drives `SocraticChat`'s `breakActive` and the 5-minute break-inactivity logout, so a voluntary break is still a real break in every safety sense.

**Mathematics is in every `COMPANION_MODES` preset**, deliberately: it's foundational, and it's the only subject carrying the full `services/diagnostic/` engine, so a family on `book_companion`/`guided` previously got no mastery signal at all — which made "mastery-based outcome" untrue for exactly the families most likely to need it. Still removable by hand; just never omitted by a preset.

**Bible translation preference.** `SessionConfig.bible_translation` (`models/schemas.py`) is a second, narrower optional field in the same panel — not "what does this family believe" but "what wording should Bede's own quoting/paraphrasing of Scripture match." `BIBLE_TRANSLATIONS` (also `models/schemas.py`, mirrored in `homeschool-tutor/src/types/index.ts` — same duplication convention as `VALID_GRADES`/`DEMO_GRADES`) deliberately spans both Protestant editions (KJV, NKJV, ESV, NIV, NASB, NLT, CSB) and Catholic editions (RSV-CE, NABRE, NRSV-CE, Douay-Rheims), same reasoning as `scripture` existing alongside `saints` rather than assuming one tradition's preferred text. `_bible_translation_note` (`services/ai_service.py`, wired into `_build_subject_prompt` for the three subjects `_faith_tradition_note` covers — `Subject.scripture`/`Subject.saints`/`Subject.morning_time` — plus every subject in `_CLASSICAL_LANGUAGE_SUBJECTS` (`Subject.latin`/`Subject.greek`), see the two sections above) is guidance only, never a verbatim quote catalog the way `services/prayer_catalog.py`'s daily prayer rotation is — Bede still quotes/paraphrases from its own knowledge, just oriented toward the stated translation's wording. `ParentSetup.tsx` renders it as a `<select>` (not free text, unlike `faith_tradition`) gated on `scripture`/`saints`/`morning_time`/`latin`/`greek` — a wider gate than `faith_tradition`'s, since `morning_time` is in the default subject list and already includes daily Bible reading for every family, not just those with an explicit faith module enabled.

**Public-domain vs. copyrighted translations — closing a real accuracy/licensing gap.** `PUBLIC_DOMAIN_BIBLE_TRANSLATIONS` (`models/schemas.py`, `{"KJV", "Douay-Rheims"}`) splits `BIBLE_TRANSLATIONS` into two groups `_bible_translation_note` treats differently, added on an explicit instruction not to let Bede present unverified wording as fact. KJV and Douay-Rheims are genuinely public domain, so Bede may favor their exact wording as freely as its own knowledge allows. Every other option (NKJV, ESV, NIV, NASB, NLT, CSB, RSV-CE, NABRE, NRSV-CE) is a modern, actively copyrighted translation owned by its own publisher (Crossway, Biblica, the Lockman Foundation, Tyndale, Holman, the USCCB for NABRE, and so on).

A follow-up research pass looked up each publisher's own actual stated permission-to-quote policy — `data/bible_translations/copyright_permissions.json` (see `docs/CONTENT_CONTRIBUTING.md`'s own entry for the sourcing standard), fed by `services/catalog_service.py`'s `get_bible_translation_permission()` — rather than assuming a blanket restriction. The real numbers are generous: 500 to 1,000 verses (or, for NABRE, 5,000 words, the unit the USCCB itself states) without formal permission from any of the nine publishers, far beyond anything a single tutoring turn would ever approach. So licensing was never really the binding constraint here. `_bible_translation_note` now says so explicitly, citing the family's translation's real, sourced limit — but the constraint that actually governs Bede's behavior is **accuracy**: Bede has no verified, licensed copy of any of these nine translations to check its own memory against, so it cannot guarantee its "recollection" of a specific translation's exact wording is correct, independent of how much that publisher's license would otherwise permit. The note tells Bede to paraphrase by default, keep any direct quotation to a verse or two it's genuinely confident about, always cite book/chapter/verse so the family can check the exact text themselves, and never present uncertain wording as though it were that translation's precise text — the constitution's "never fabricate certainty" rule applied specifically to a text Bede cannot verify, the same failure mode as inventing a fact or a source. An explicit closing line keeps this from being misread as license to thin out the lesson itself: Bede still narrates Scripture's real people and events fully and keeps asking real Socratic questions — Charlotte Mason/Mater Amabilis narrative teaching and this app's Socratic method (`docs/SOCRATIC_METHOD.md`) are untouched; only literal verbatim wording needs the extra care. `ParentSetup.tsx`'s hint text under the translation picker states the public-domain/copyrighted distinction plainly to the parent rather than leaving it implicit. Covered by `tests/test_bible_translation_note.py` and `tests/test_catalog_data_integrity.py`.

**Curriculum resources the family already uses.** `SessionConfig.curriculum_resources` (`models/schemas.py`) is a third, general-purpose field in the same panel — a list of up to 6 curriculum publisher/resource names (`_validate_curriculum_resources` trims, drops empties, dedupes case-insensitively, and caps at 6, the same "clean, never reject" shape `_validate_term` already applies to `term_mastery_topics`). Deliberately narrow in what it asks Bede to do: align terminology/approach where it naturally overlaps with a named resource's known general method, but explicitly **never** claim to reproduce that publisher's actual proprietary lesson content — unlike `data/catechism/faith_and_life.json`'s sourced Ignatius Press scope-and-sequence, there is no verified dataset backing these names, so treating them as anything more than a name to align tone with would risk the exact kind of fabricated certainty the constitution's first non-negotiable rule forbids. `ParentSetup.tsx` renders it as a comma-separated free-text input (same editing convention as `term_topics`) with six quick-pick suggestion chips that append themselves into the field — always visible in the session-context panel (not gated to any subject), since these resources aren't specific to the faith modules.

```
**The drawing area itself now fills a landscape screen edge-to-edge, via cover-and-scroll rather than shrink-to-fit.** The `short:` toolbar compaction above only reclaimed the toolbar's OWN share of a landscape window's height — the page itself was still letterboxed (shrunk to fit entirely inside whatever height was left, per its own 8.5:11 proportions), so most of a wide landscape screen still sat empty on both sides even after the toolbar was as small as it could get. Real screenshots (not a guess — see the PR that shipped this) showed a landscape phone using only ~15% of its screen. The `paperBox`-fitting effect (above `initCanvas`) now branches on backdrop shape: **landscape-shaped backdrop** (`availW > availH`) fills the FULL height (never just "contain" to whichever dimension is smaller) and lets width extend to match — since an 8.5:11 page is always proportionally narrower than a landscape window, this never overflows width, so it's a pure win with no downside; the backdrop's `overflow-hidden` became `overflow-auto` so the part of the page below the visible strip is one scroll away. **Portrait-shaped backdrop is deliberately left as pure "contain," unchanged** — the same cover math in portrait would require the page to overflow SIDEWAYS instead (an 8.5:11 page is proportionally *wider* than a narrow phone screen, the opposite relationship from landscape), which was measured and rejected as a worse experience than portrait's small existing gap: scrolling left-right to reach a notebook page's side margins is an unusual gesture, versus a modest, non-interactive empty strip below the page today.   audioSession.ts    Best-effort wrapper around WebKit's `navigator.audioSession` (iOS/iPadOS 17+ only, feature-checked + try/catch elsewhere): `enterRecordingAudioSession()`/`restorePlaybackAudioSession()`, called from `useHybridVoiceInput.ts` — see that hook's own entry above and docs/VOICE_SETUP.md
  canvasPersistence.ts  Keeps `HandwritingCanvas.tsx`'s page alive across a switch back to Bede and no longer. The canvas unmounts every time the child returns to the chat, so before this every stroke died with it, unwarned - the same silent-loss class `utils/logoutNotice.ts` exists to refuse. Three properties carry the design: **sessionStorage, never the server** (a work-in-progress drawing is an artifact, not a claim about the child, so it is not database material by this codebase's own `MasteryProfile` vs. `SkillActivityLog` distinction, and a per-tab store means no retention question for a parent to answer); **a stated budget, enforced** (`CANVAS_BUDGET_BYTES`, 2 MB, roughly 100k stroke points in the flat `[x, y, pressure, ...]` encoding - passing it drops the stored page and REPORTS that, so the child can save it to their device while it is still on screen, rather than finding half a drawing later); and **one page per session per device** (`pruneOtherPages` drops another student's page, so the cap bounds the tab rather than being a per-student allowance that adds up). `parsePage` validates rather than trusts, since a reload-surviving store is editable in devtools and a malformed page must produce a clean sheet, never a crash inside the draw loop. Coordinates are rounded to a tenth of a canvas unit (~1/1000 inch at print scale, measured as under 64/255 of antialiasing difference in a real browser) purely to buy drawing headroom inside the same budget. `demo/src/canvasPersistence.ts` is the demo's own mirrored copy (same reasoning as `demo/src/holdGesture.ts`), keyed by the demo session code rather than a student name, with a stroke shape matching that canvas's own (`isEraser`, no pencil). It used to also carry a `space` field (the CSS-pixel size a page was drawn in) plus a rescale-on-restore step in `HandwritingCanvas.tsx`, because that canvas sized its backing store to whatever the element occupied and a page restored into a differently-shaped window would otherwise land crooked. Both are gone as of the print-resolution follow-up below - `CANVAS_STORAGE_VERSION` bumped 1 → 2 for the dropped field, same abandon-not-migrate policy this module has always used. **Why they're gone**: `demo/src/HandwritingCanvas.tsx` now draws into the same fixed 816x1056-at-96-DPI physical page (`CANVAS_WIDTH`/`CANVAS_HEIGHT`/`PRINT_DPI`) the app's canvas has used since PR #402, letterboxed on screen via a `paperBox`/`wrapperRef`/`ResizeObserver` effect and rescaled through `getPos`'s `canvas.getBoundingClientRect()` math, rather than sizing its backing store to whatever CSS box the flex layout gave it. Before this, the SAME drawing produced a different-resolution PNG depending on how big the visitor's browser window happened to be - a phone-width viewport saved a correspondingly low-resolution keepsake - and print output was similarly window-shape-dependent rather than true-to-scale Letter paper; both are now pinned to the physical page regardless of window size, closing that specific gap raised in review of #403. One further, structural cleanup this unlocked: the two "page not being kept" notice bars had been drawn as an absolute overlay on the paper (a review fix for #403, since the old variable-sized backing store meant a notice appearing on its own would shrink the canvas box out from under an already-rendered bitmap and misalign every new stroke from the stylus) - with the backing store now fixed and pointer mapping always going through the bounding-rect rescale, that failure mode is structurally impossible, so the notices are back to being ordinary flex-column siblings above the paper, matching the app's own layout, and the overlay markup was removed rather than left as unnecessary complexity. The demo's `handleLogout` clears the page alongside `clearChatState`, and every key it writes is named in `site/privacy/index.html`'s storage inventory - that page promises "every piece of browser storage... with no rounding up", so a key added here without a row there makes it publicly wrong, which `demo/src/privacyInventory.test.ts` now fails on rather than leaving to memory (same two-copies-of-one-fact pattern as `homeschool-tutor/src/i18n/docQuotes.test.ts`). Three rules the review of that port turned up, now true of BOTH copies: a refusal and the "start fresh?" question are **separate state**, so answering "Never mind" uncovers the refusal again instead of leaving a child unsaved with an empty bar; the **unmount flush passes `dropStoredOnRefusal: false`** (`SaveOptions`), since that is the one path with no UI left to report a refusal and dropping the last good page there would be a silent, unexplained loss; and a **page with no strokes that has never been written is not written at all**, so "New page clears the stored drawing" stays literally true rather than being followed by an empty page on the way out. The debounce also has a ceiling (`PERSIST_MAX_WAIT_MS`): every stroke restarting it meant a child who never pauses was never saved, and a page never saved is also a page whose budget is never checked, so the warning would have arrived only once it was too late. `handleSaveToDevice` (both copies, `HandwritingCanvas.tsx`) revokes its blob URL after `SAVE_URL_REVOKE_DELAY_MS` (60s), not a bare `setTimeout(...,0)`: Safari/iOS has a documented history of treating an object URL as already gone if it's revoked while the download is still being read from it, and a same-tick timeout doesn't clear that window on a slow mobile connection - a one-off PNG costs nothing to hold a minute longer, and this specific failure mode can't be verified against a real device from this sandbox, which is exactly why the fix errs long rather than clever
  safeRedirect.ts    `safeReturnTo(raw, fallback)` / `isSafeReturnTo(value)` — the ONLY sanctioned way to turn `Login.tsx`'s `?returnTo=` query parameter into a `navigate()` target. Every redirect there fires AFTER `setAuth()`, so an unvalidated value hands a just-authenticated parent or child to an off-site page (see docs/SECURITY.md's Closed gaps). Validates the DECODED string (checking the encoded form and navigating to the decoded one is its own bypass), rejects protocol-relative/backslash/control-character forms, and finishes with a `new URL()` origin check rather than trusting its own string reasoning. Note the app imports from `react-router`, NOT `react-router-dom` — the shim stops at 7.18.2, inside a later advisory's range, while `react-router` continues to 8.3.0 and is clear
  holdGesture.ts     `createHoldHandlers({onStart,onEnd}, state)` — pointer wiring for the press-and-hold mic (mirrored to `demo/src/holdGesture.ts`). Same technique `HandwritingCanvas.tsx` already used for drawing strokes. Distinct from continuous "Voice on" mode's missing endpointing, which is still open
```

### Key Frontend Flows

**Child session URL flow:** Parent copies `/session?student=Emma` to tablet → `RequireAuth` redirects to `/?returnTo=%2Fsession%3Fstudent%3DEmma` → child logs in with PIN → `fetchStudentConfig` loads config → navigate to session. `AppShell` deliberately does NOT redirect unauthenticated users (that's `RequireAuth`'s job — a prior bug where AppShell did this stripped the `returnTo` param).

**Zustand store:** `persist` middleware saves only `{token, role, sessionConfig, podStudents}` to `sessionStorage`. Chat history and streaming state are never persisted. `getApiMessages(displayMessages, subjectStart)` slices the message array to the current subject's history before sending to the API.

**Subject opener:** `openerFiredRef = useRef(new Set<string>())` gates exactly one `[START]` send per subject. `sendOpener` reads live store state via `useSessionStore.getState()` (not the hook closure) to avoid stale-closure issues during streaming.

**Streaming state machine:**
```
startAssistantStream() → adds empty 'streaming-response' placeholder
appendAssistantChunk() → mutates placeholder content
addToolMessage()       → finalizes placeholder text, inserts tool card, reopens placeholder
finalizeAssistantMessage() → promotes placeholder to a real message, sets isStreaming=false
```

## Models

Which model actually serves a tutor turn now depends on `services/adapters/` (see
above) — the first *configured* adapter in `BEDE_ADAPTER_ORDER` wins, and each
adapter has its own model setting in `core/config.py`:

- **Anthropic** (`tutor_model`/`session_model`) — `claude-sonnet-4-6` (streaming,
  `max_tokens: 400`, tight for Mater Amabilis brevity) /
  `claude-haiku-4-5-20251001` (non-streaming, `max_tokens: 600`, end-of-session
  parent report). This is the model pair a self-hosted deployment gets when
  `anthropic` resolves (the library default, `local,anthropic`, falls through
  to this once `ANTHROPIC_API_KEY` is the only thing configured).
- **OpenAI** (`openai_model`, default `gpt-4.1-mini`) and **Mistral**
  (`mistral_model`, default `mistral-large-latest`) — the models the public
  Render demo actually uses in production, since its
  `BEDE_ADAPTER_ORDER=openai,mistral` (OpenAI primary, Mistral as the live
  failover if OpenAI errors mid-request).
- **Local** (`local_llm_model`, default `Qwen/Qwen3-Coder-30B-A3B-Instruct`) —
  the self-hosted vLLM option; needs a GPU (see docs/PROVIDER_ADAPTERS.md's
  hardware tiers).

To change which model a given adapter uses, update its `*_model` setting in
`core/config.py`; to change which adapter wins, update `BEDE_ADAPTER_ORDER`
(or `render.yaml`'s copy of it for the demo).

**Tool registry — what each agentic tool IS, declared rather than implied:**
`services/tool_registry.py` holds a frozen `ToolSpec` per tool
(`reactable`/`terminal`/`silent`/`questionless`/`trust`), and
`stream_tutor_response`'s loop reads it instead of re-deriving the same
facts from `tc["name"] == "..."` comparisons buried ~1200 lines from the
tool's own schema. Before this, three things were true and none was
visible: a tool added to `TUTOR_TOOLS` with no matching branch fell
through to `_process_tool_use`, returned `""`, and emitted nothing
(silent); no test could check the set for completeness; and where a
tool's result CAME FROM was written down nowhere, because there had only
ever been one answer. `trust` is that last one made explicit — CLAUDE.md
already stated the invariant the tool_result loop rests on (fixed,
server-computed data, never anything sourced from outside this process)
and it had no representation in code.
`tests/test_tool_registry.py::test_every_tutor_tool_is_internal` fails if
it stops holding. This is what lets an external-trust tool exist elsewhere
in the process while remaining **structurally** incapable of reaching a
child: `TUTOR_TOOLS` contains only internal specs, so the tutor loop
cannot dispatch an external tool even if one is registered. Every
predicate defaults False for an unrecognized name, so a hallucinated tool
can neither buy itself extra model round-trips nor force a turn to end.

**MCP server — Bede's parent data, readable by an assistant the parent
already uses (`scripts/mcp_server/`, `docs/MCP.md`):** answers "can I ask
about my kids' progress from where I already work instead of opening the
parent dashboard." Deliberately the *server* direction first, and
deliberately **not** mounted in the FastAPI app: an MCP endpoint inside
the API would add a new authenticated network surface to the very process
that serves children, whereas a stdio server launched by the parent's own
MCP host adds none — no new port, no new endpoint, and it reaches Bede
through the same authenticated REST endpoints the parent UI already uses.
Data flows OUT, so there is no injection surface into a child's context
at all, which is what makes this the highest value-per-unit-risk piece of
MCP work available here. Six read-only tools (roster, mastery summary,
work ledger, pod roster, narration history, learner profile), all
annotated `read_only_hint` in the protocol itself. Read-only-ness is
structural rather than promised: `bede_tools.py`'s only request helper is
GET-only, and `test_every_tool_issues_only_get_requests` asserts it by
watching real traffic rather than reading the source. **The refusals
travel with the data** — the pod roster is not a ranking, an unscored
activity is a blank and not a low mark, a cold-start mastery estimate is
provisional, `processing_style` is not a psychometric claim — and since a
consuming model can reintroduce a ranking the data doesn't contain just
by summing, each refusal is written into the `TOOL_SCHEMAS` **description
the model actually reads**, with tests pinning that it is still there.
`test_no_tool_exposes_anything_about_faith_engagement` makes adding a
spiritual-engagement metric fail a test rather than pass a review.
Parent MFA is an accepted hard stop (no browser, so no ceremony) reported
as an actionable message, never worked around. **Registers itself as a
device** (`LoginRequest.device_id`, P9) so a parent can revoke it from
device settings like any tablet — sending one is optional at the API, and
a caller that omits it can never be revoked, which is precisely why this
one doesn't: the process holds a parent password and reads every child's
progress. Split into a dependency-free tool layer (`bede_tools.py`,
unit-tested) and a thin transport (`server.py`), so `mcp` stays out of the
API image and its pip-audit gate — with `test_server.py` covering the seam
between them and `e2e_check.py` (run by hand) covering the wire contract.
Both exist because of defects a green unit suite missed: the first cut of
`server.py` was written against the SDK's 1.x decorator API and could not
start at all, and `bede_tools.py` sent `password` where `LoginRequest`
requires `credential` — a guaranteed 422 against a real deployment, which
survived because the unit tests stubbed the transport and the e2e stub
accepted any JSON body. `e2e_check.py`'s stub now validates with the API's
own pydantic model, and was verified to FAIL when that bug is
reintroduced. The general rule: a fake looser than the real thing is not a
test, it's a second place for the bug to hide.

**Content curation gate — growing the library without diluting mastery
(`services/content_curation.py`, `scripts/curate_content.py`,
`docs/CONTENT_CONTRIBUTING.md`):** that doc already stated how content is
added (never store copyrighted text, cite a primary source, match the
schema) but could not enforce any of it — every rule was a paragraph a
reviewer had to remember, on a repo whose own standing workflow says a
decision is finished only when the code says the same thing. `curate()`
turns the mechanical parts into a gate and adds the constitutional checks:
verbatim text needs a cited primary source and must be public domain; known
misattributions are flagged (seeded from the real `ora_et_labora` finding —
it appears nowhere in St. Benedict's Rule; warn rather than block, since it
may be quoted precisely to correct it, which is what `latin_catalog.py`
does); living books must declare `anti_twaddle`; Logic content may not
target K-2 (the fifth route into that gate, now closed too); proposed
activities are scanned against `_physical_safety_guardrails()`' hazard list,
which constrains Bede's OWN words and so says nothing about material handed
to it; `scripture`/`latin`/`greek` must stay usable by any Christian
tradition while `saints` may carry Catholic-distinctive material by design;
and **any field resembling a faith-engagement metric is refused outright** —
a content field is as good a place to introduce one as a database column.

**The mastery-linkage rule is the one that makes a growing library safe.**
Every candidate must declare which existing diagnostic skills it exercises,
validated live against `services/diagnostic/`'s own vocabularies
(`skill_map`/`phonics`/`literacy`/`composition`/`language_exposure`), or set
`exercises_no_tracked_skill=True` to say plainly that it exercises none — an
empty list alone is refused, being indistinguishable from a field nobody
filled in (the same instinct as refusing to let a blank score look like a low
one). **Content may not invent a skill id**: `MasteryProfile` stores those
ids as the only link to a family's accumulated history and there is no
`ALTER TABLE` path, so growing a map is a deliberate, separately-reviewed,
strictly-additive change, never a side effect of adding a poem. Without this,
a freely-growing library and a standing diagnostic drift apart and the
symptom a parent sees is their child appearing to fail at material Bede never
taught — the exact drift `tests/diagnostic/test_prep_school_scope.py` exists
to prevent. `CurationVerdict.accepted` deliberately means "nothing mechanical
is wrong", never "this belongs in a child's year"; a human still reviews
that, and both the module and the CLI say so.

**Session planner — the one planning decision Bede is competent to make
(`services/lesson_planner.py`, `GET /diagnostic/{student}/plan`):** before
this, Bede had no planner at all — the "plan" was the parent's subject list
plus fixed `SUBJECT_DURATIONS`, and its only sequencing authority was
`suggest_next_subject`. Mastery data shaped questions *within* mathematics
(`get_next_probe_hint`) but nothing ever looked across the day. **It orders;
it never chooses.** `plan_session` returns a permutation of the parent's own
subjects — never one added, dropped, or shortened — which is the
constitution's `authority_order` (the parent is the child's primary
educator), not a conservative implementation choice;
`test_plan_is_always_a_permutation_of_the_parents_subjects` pins it. A pure
function with no I/O, following `services/policy_engine.py`'s precedent.
**Faith-formation subjects (`morning_time`/`scripture`/`saints`) are
ANCHORED to the parent-given position**, not merely excluded from promotion:
the first cut only skipped promoting them, and a Scripture block still slid
to the END of a day whenever the ordinary subjects around it went stale — no
number was ever computed about the child's spiritual life, and the timetable
said something about it regardless, which is precisely what the
never-measure-faith rule exists to prevent. Position is now held against
movement in **either** direction (`_place_anchor`, and when a slot is
contested it prefers to stay later, since moving a faith subject *forward*
is the direction that reads as Bede pushing it). `latin`/`greek` are
deliberately NOT anchored — they are language subjects that draw on
Christian texts, and ordering them by recency says nothing about a child's
spiritual life. What *does* drive the order: Morning Time opens the day
(Mater Amabilis convention), then a parent's own `lesson_resume` note (an
explicit instruction outranks any convention of Bede's), then cognitively
demanding subjects while attention is freshest, then subjects whose
`LessonBookmark` is stale (>= 14 days, the same threshold `_bookmark_note`
uses for its own "a while back" phrasing), with `free_study` closing.
**Every reason is a fact about the PLAN or about ordinary pedagogy, never
about the child** — the same distinction the mastery cycle draws when it
reports missing evidence as a finding about the schedule; a test scans every
reason string for judgment words. **Advisory and parent-only**: the endpoint
reports an ordering and does not apply one, and a child never sees it — "Bede
put maths first because you haven't done it in a while" is something about
themselves that Bede has no standing to say.

**MCP client — Bede consulting a parent's own MCP servers
(`services/mcp_client.py`, `docs/MCP.md`):** the inbound counterpart to the
server above, and the only path in the system by which content that did not
originate inside this process reaches model context. That single fact
governs the whole design. **Confined to the parent sandbox** by three
independent mechanisms, not one setting: `TUTOR_TOOLS` holds only
`trust="internal"` specs so the tutor loop cannot dispatch an external tool;
`stream_sandbox_response` takes `external_tools` as an argument defaulting to
none rather than reading settings itself; and `/sandbox/demo-chat` — which
any anonymous visitor with a demo code can reach, and which shares that same
function with the parent's `/sandbox/chat` — never passes it.
`tests/test_mcp_sandbox_boundary.py` pins all three, the last one as a
source-level assertion that the demo call site does not mention these
arguments at all. The redundancy is deliberate: the failure being prevented
(a child, or a stranger, reading attacker-authored text in Bede's voice) is
one you learn about afterwards. **Off by default**, and requires BOTH
`MCP_EXTERNAL_ENABLED` and a non-empty `MCP_EXTERNAL_SERVERS`, so half-arming
it does nothing. Every result is `_redact_credentials`'d, run through the same
`_INJECTION_PATTERN` applied to parent-supplied `SessionConfig` fields,
truncated to `MAX_RESULT_CHARS`, and wrapped in an
`<untrusted_external_content>` envelope — guidance rather than a guarantee,
which is exactly why the structural confinement above carries the real
weight. Tools are namespaced `mcp__<server>__<tool>`, making collision with
an internal tool impossible rather than checked-for. The client declares
**no capabilities** at initialize, notably not `sampling`, which would let a
remote server ask Bede's own model for completions and spend a family's
tokens. `AuditEvent.EXTERNAL_TOOL_INVOKED` is its own event rather than
folded into `TOOL_INVOKED`, since "outside content entered model context" must
stay distinguishable from Bede consulting its own catalog; its anomaly
threshold (12/10min) is far tighter than `TOOL_INVOKED`'s 40. A hand-rolled
JSON-RPC client over httpx rather than the `mcp` SDK, keeping that dependency
out of the API image and its pip-audit gate — with
`homeschool-api/scripts/mcp_client_e2e_check.py` (run by hand) validating it
against a REAL SDK-built MCP server over a real socket, because unit tests
against a stub this repo wrote can only confirm the client agrees with our own
reading of the spec. Bede never spawns a subprocess for this: the API
container runs `read_only` with `cap_drop: ALL`, so an outbound HTTP call to
an address the parent named is a far smaller change to the deployment's
threat model than launching local commands.

**Beta surveys — one instrument, three delivery channels
(`docs/BETA_SURVEY.md`):** the beta period has three decisions to make
(does the pedagogy land, what should this cost and in what unit, are
co-ops a real channel) and, before this, one general "tell us what to fix"
form (`site/feedback/index.html`) aimed at none of them. The word "co-op"
appeared twice in the entire repository, both times in passing, which is
the size of that particular gap. `docs/BETA_SURVEY.md` is the **source of
truth**: two instruments (beta parents; co-op educators), the reasoning
behind every question, and the rules governing what a survey here may ask.
Change a question there first, then in the channel.

- **`site/survey/index.html`** (`/survey/`) and **`site/educators/index.html`**
  (`/educators/`) are the primary channel, and the only one that reaches a
  co-op leader who has never opened Bede. **`BetaSurveyModal.tsx`** is the
  short in-app leg for parents already using it. All three post to
  `POST /feedback` → Resend → `FEEDBACK_EMAIL` (`info@agnusdei.ai`, set in
  `render.yaml`) under one `beta_survey` category so their answers pool;
  each tags its own message body so the inbox can still tell them apart.
  The hosted pages have no session, so they mint one the way a demo visitor
  does (`POST /auth/demo-code` → `demo_code` JWT → submit) — which needed no
  backend change at all: `agnusdei.ai` was already in `CORS_ORIGINS`, and
  `site/_headers`' single site-wide CSP already allows
  `connect-src https://*.onrender.com` because the demo under `/bede/`
  needs the identical permission.
- **The API's URL is filled in by the build, not by hand.**
  `site/assets/api-base.js` ships empty (`window.BEDE_API_BASE = ''`) and
  `scripts/build_pages_site.sh` overwrites it in `publish/` from
  `VITE_DEMO_API_BASE` — the same variable `demo/src/api.ts` already
  consumes, so the value is configured once on the Worker rather than
  committed as a second copy someone has to keep in step. The build
  validates it is a plain `https` origin before writing it into a script
  served to every visitor, and trims trailing slashes so the value is
  canonical. Unset is a supported outcome, not a failure: the forms fall
  back to the visitor's own mail client, and the build prints which of the
  two happened — otherwise the only symptom of a lost variable is an inbox
  that quietly stays empty while every form still appears to work.
  Because this makes those static pages contact the API at all,
  `site/privacy/index.html` had to move with it: it now states that the
  pages make no network request until a visitor presses play on the home
  page's video or send on a form, and carries a table row for the forms.
  That page promises a complete, code-audited inventory, so wiring this up
  without amending it would have made a public privacy claim false.
- **A fully-answered survey does not fit in a `mailto:` link.**
  `MAILTO_SAFE_LENGTH` (1900) was sized for the twelve-field feedback form;
  these are twice that, so overflow is an ordinary outcome here rather than
  an edge case, and it is reached on the only delivery path those pages
  currently have. The original behavior — tell the visitor to "shorten the
  longer answers" — breaks these pages' own promise that nothing they typed
  is lost, at the worst possible moment. `handOffToClipboard` renders the
  assembled message back into a read-only textarea with a copy button and a
  `mailto:` link instead. Pinned by filling both surveys completely in
  `demo/src/surveyForms.test.ts`, verified to fail when the fallback is
  reverted.
- **`site/assets/feedback-form.js` is one script for every form on the
  site** — the home page's own "Request a call" as well as the three
  hosted pages — configured per page by `data-category`/`data-tag`/`data-mail-subject`
  on its own `<form>`. Its question labels are read from each page's own
  `<legend>`/`<label for>` rather than from the hardcoded field-name map it
  used to carry — that map was a second copy of every question, whose
  failure mode was an answer arriving in the inbox filed under wording no
  longer on the page. `demo/src/surveyForms.test.ts` loads the real pages
  into a real DOM, runs the real script, and asserts the assembled message;
  verified to fail on each page when the DOM lookup regresses. The home
  page was **missing from that list** until the pass that rebuilt its form
  around a dropdown and option tiles, even though it runs the same script
  through the same code path — and it is the one form whose silent failure
  costs a sales lead rather than a survey answer.
- **The category string is the same fact in four files** — a pydantic
  `Literal`, two HTML attributes, and a TypeScript call site. Nothing
  type-checks a static site's markup against a `Literal`, so a typo would

Deleting the two origins from a family's own CSP degrades picture study to the captioned card rather than breaking it, which is what makes it a choice.
- **The home page's video is the one element that opts out of `Referrer-Policy: no-referrer`, and it has to.** `site/_headers` sets that policy domain-wide, mirroring `core/middleware.py` and `nginx.conf`; since late 2025 YouTube's embedded player refuses to start unless an HTTP `Referer` identifies the embedding host, and shows **"Error 153 — Video player configuration error"** in its place. That is a header-level failure, so it hits every visitor and every browser at once, and it reached us as a screenshot rather than a report from the site itself. `site/assets/video.js`'s iframe therefore carries `referrerpolicy="strict-origin-when-cross-origin"` — an element attribute overrides the document policy for that element's own request, so the exception stops at this one iframe and the rest of the domain keeps sending nothing. The value is the **narrowest that works**, not the first that works: `unsafe-url`/`no-referrer-when-downgrade` also clear error 153 and hand YouTube the full page URL, which would make `site/privacy/index.html`'s stated inventory (origin only, never the page you were reading) false — that page is a promise of a complete audit, so it carries a line about what pressing play sends. `homeschool-api/tests/test_youtube_embed_referrer.py` pins the two files against each other, including the leaky-fix direction. Verified live in real Chromium against a server sending the real `_headers` values (no referer before, `https://<origin>/` after, query string withheld) — jsdom evaluates no referrer policy at all, so this class of bug is structurally invisible to a component test, the same limitation `HandwritingCanvas.tsx`'s `short:sr-only` fix ran into.
- **Every form on the marketing site carries `method="post"`, and that attribute is a privacy control rather than a route.** Nothing accepts a POST — `site/assets/feedback-form.js` intercepts submit and sends the answers itself — but all four buttons are real `type="submit"` buttons (deliberately: Enter-to-submit, and the browser's own `required` validation), so if that one script ever fails to load or parse the browser performs a NATIVE submit. With no method that is a **GET to the same static page**, which writes every answered field into the query string — name, email, and on `/survey/` and `/educators/` several paragraphs of free text — and so into browser history and any URL-logging intermediary. CSP's `form-action 'self'` keeps it on this origin; it does not stop it being written down. As a POST the same failure loses the answers instead of publishing them, and every one of these forms already shows a mailto address in its own note as the way to send them. `homeschool-api/tests/test_site_form_markup.py` pins it — alongside a second guard from a defect made while adding the first: an HTML comment opened **inside** an opening tag is not a comment, because `-->` contains the `>` that closes the tag, so the remaining attributes render as visible body text (`method="post" data-category="cx" …` appeared above the feedback form). Nothing errors and nothing fails to build; it is visible only to someone looking at the page.

- `ExfiltrationGuard` middleware blocks known exfiltration endpoints (`/export`, `/download`, `/dump`, `/backup`, `/debug`) and, for buffered JSON responses only, scans the body for leaked key material (`embedding` arrays, `data_key`, `device_salt`, the SAGE encrypted-file magic) before returning it — capped at 2MB. It deliberately does NOT buffer or re-scan `text/event-stream` (the `/tutor/chat` SSE stream): prompt-injection defense for that path relies on the model's own training plus the constitution's `<ethical_boundaries>` rules rather than input-side filtering. `_sanitize_parent_field`/`_INJECTION_PATTERN` (`services/ai_service.py`) strip injection phrasing out of *parent*-supplied `SessionConfig` fields specifically (`faith_emphasis`, `lesson_focus`, `current_unit`, topics) — those sit in the cached static prompt block for the whole session — but never the child's own live per-turn chat text; there's no server-side secret in Bede's context for a jailbroken turn to leak in the first place. **One documented exception, and the reason to check before adding another:** that "child text is transient, so leave it" reasoning holds only while the text really is transient. `LessonBookmark` breaks both halves — the summary model writes each resume sentence from a conversation the child fully steered, and `_bookmark_note` replays it into that subject's prompt at the start of every future session. So bookmarks ARE sanitized, on both the write path (`_persist_lesson_bookmarks`) and the read path (`_bookmark_note` — deliberately both, since rows written before that fix are still live in deployed databases and there's no `ALTER TABLE` path to clean them). ## Standing Workflow: Root-Cause Fixes

When you find and fix a root cause (a bug, a performance issue, etc.) in
this repo, don't stop at opening a PR and waiting — drive it to done:

1. **Test first.** Verify the fix actually resolves the issue before doing
   anything else. Prefer a real end-to-end check over a code-reading
   argument — e.g. for a GitHub Actions workflow, trigger it for real
   (`workflow_dispatch`) and read the job logs, rather than asserting the
   YAML "looks right." If a live check isn't reachable from the sandbox,
   say so explicitly rather than claiming full verification.
2. **Open a PR** once the fix is confirmed to work, with a test plan in the
   body describing exactly what was verified and how.
3. **Merge it automatically** — do not wait for manual approval on this
   repo. This authorization stands until the user says otherwise.
4. **Tell the user** once it's merged (and, where applicable, live) so they
   can do their own testing.

This is a standing rule for this repo across sessions, not a one-off for
whichever task prompted it.

**Carve-out for the public-facing demo/marketing pages (`site/`, `demo/`):**
step 3 above does NOT apply to changes under these two directories. Instead:
run a thorough self-review (the `/code-review` or `/security-review` skill,
whichever fits the change) on the diff, report the findings, and then wait
for the user's explicit sign-off before merging — no auto-merge. These paths
are the first thing a prospective family sees, and copy/content changes in
particular (not just code) carry a higher risk of drifting from what the
product actually does, so they get an extra human checkpoint the rest of the
repo doesn't require. Everything else about the workflow (test first, open a
PR with a real test plan, tell the user once merged) still applies.

## Standing Workflow: Carry Out the Decision, Don't Just Record It

A design decision is not finished when it is written down. It is finished
when the code, the docs, and the user-facing copy all say the same thing.
**Do not leave a gap between a decision and its execution**, and do not
close a piece of work with a "still to do" that quietly hands the gap to
whoever comes next.

This rule exists because this repository has repeatedly produced exactly
that gap, and each time the gap was invisible in the place someone would
look for it:

- `DiagnosticEvidenceLog`'s docstring said "opt-in and off by default"
  for four phases after `docs/diagnostic/DIAGNOSTIC_ENGINE_DESIGN.md`
  §5.3 recorded the flip to `True`. A deployer reading the model to
  decide what their database held would have concluded the table stayed
  empty. The decision was recorded; it was never carried into the code
  it described.
- The site said "Eleven subjects" for three shipped subjects, because
  the decision to add them stopped at the app.
- A subject rename landed in `models/schemas.py` and not in `site/`,
  twice, because the two live in files that never conflict in git.
- A readability pass cleared dash overuse from every page, and copy
  written days earlier missed the sweep, so one document contradicted
  the style the same repository had just adopted.

**In practice this means:**

1. **Finish the sweep.** If a rule now applies (a rename, a style, a
   guarantee), apply it everywhere it holds in the same change, not to
   the file that prompted it. Grep for the old form and prove it is gone.
2. **Where the same fact lives twice, make one check that they agree.**
   A UI string quoted verbatim in a doc, a label duplicated between
   `schemas.py` and `types/index.ts`, a constant mirrored in two
   languages: add the assertion that fails when they drift, rather than
   trusting the next person to remember. `tests/test_catalog_coverage.py`
   and the `SUBJECT_LABELS` parity check are the pattern.
3. **A spec that stays unbuilt needs a reason, not a status.** "Proposed"
   is legitimate only when a decision genuinely belongs to the founder
   (scope, product direction, a privacy posture). Anything blocked only
   on effort gets built.
4. **State what remains, and why, in the same breath.** If part of a
   change genuinely cannot land yet, say which part and what blocks it.
   Silence about a gap is what turns it into a defect nobody owns.

This is a standing rule for this repo across sessions, not a one-off for
whichever change prompted it.

## Standing Workflow: Feature Documentation

Every feature or user-facing behavior change introduced to this repo needs
to be documented as part of that same change — not left as a follow-up. A
feature is not done until its documentation is:

1. **Parent-facing controls and behavior** — `docs/PARENT_SETUP.md` (the
   per-student settings live in §5 "Setting up each student"). Written as
   plain instructions to a non-technical parent.
2. **Child-facing features** (anything the learner sees or uses) —
   `docs/CHILD_GUIDE.md`, keeping its voice: Bede speaking directly and
   warmly to the child, no jargon.
3. **Setup/troubleshooting-relevant change** (voice, auth, deployment,
   backup, etc.) — update the relevant file in `docs/` (e.g. a voice-
   pipeline reliability fix belongs in `docs/VOICE_SETUP.md`, not just the
   commit message).
4. **Architectural/config change** (a new router, frontend flow, service
   module, table, SessionConfig field, or env var) — update the relevant
   subsection under `## Architecture` above so this file keeps matching
   the real codebase.
5. **Anything else user-facing** — put it somewhere it will actually be
   found later (an existing doc if one fits, a new one if none does). A
   thorough PR description is not a substitute — PRs get buried in git
   history; docs are what the next person (or session) actually reads.

Also check whether the change makes existing doc text stale (e.g. a new
setting that replaces "this isn't configurable") and fix that text in the
same change.

This is a standing rule for this repo across sessions, not a one-off for
whichever change prompted it.
